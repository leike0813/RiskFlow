# 定义完整产品目标与 MVP 完成标准

## Question

RiskFlow 的完整产品应覆盖哪些用户、业务场景与能力，哪些能力必须进入可实际运行、可私有部署、可验收的 MVP，哪些能力属于 MVP 后续；应以什么可观察结果判定 MVP 已完成，而不是只有页面、骨架或不可复现的模型输出？

## 已确认决策

### MVP 覆盖原则

采用“全链路覆盖、受限深度”作为 MVP 的范围划分原则：

- MVP 必须真实运行并可审计地覆盖风险识别 RI-S1～RI-S6 与风险评估 RA-S1～RA-S7，不得以页面、占位接口、Mock 后端或不可复现的模型输出代替业务能力。
- MVP 可以限制工程范围、资料格式、知识规模、风险规则数量、监测指标数量、并发量与外部集成数量，但不得截断识别、评估、预警、处置、反馈与校准闭环。
- RA-S7 至少实现“记录反馈 → 计算偏差 → 生成校准建议 → 人工审批 → 发布新版本”的最小可运行闭环。
- CAD 深度解析、生产级实时 MCP、多渠道自动通知、LoRA 微调、高可用和多项目规模化属于 MVP 后续能力；其中 LoRA 仅在基线模型评测表明有必要时引入。

### 产品责任边界

RiskFlow 定位为“有人监督的风险决策与闭环管理系统”：

- 系统可以自动完成资料处理、风险识别、风险评估和预警判定。
- 校验失败、证据不足、置信度不足及重大风险必须进入人工复核流程。
- 预警发布策略可配置；处置方案发布、规则校准和版本生效必须由具备相应权限的人员审批。
- 系统提供风险判断、处置建议与可审计依据，不直接控制施工设备，也不替代现场责任人作出最终安全决策。

### MVP 验收数据基准

- MVP 最终验收必须使用至少一套由甲方提供或书面认可的脱敏工程样例；样例应包含工程资料、风险规则或风险矩阵，以及完成评估所需的监测数据。
- 工程样例及其规则、输入版本与预期核查要点组成固定验收包，必须能够在私有部署环境中重复执行并保留版本记录。
- 合成数据可以用于开发、自动化测试和故障场景验证，但只能证明技术就绪；未经甲方认可的工程样例验证，不得判定 MVP 已完成。

### MVP 可操作性标准

- MVP 必须是业务人员可以实际操作的产品，不得仅交付后端、API、脚本或页面原型。
- 授权用户必须能够通过界面完成资料接入、风险识别、风险评估、预警、处置、复核、反馈与结果追溯。
- Agent 交互界面是 MVP 必备入口，并且能够引用系统内的证据、工序节点、风险记录、评估结果等业务对象。
- 日常业务流程不得依赖命令行、直接修改数据库或由开发人员手工串联；部署、模型装载和底层运维可以使用配置文件及管理命令。

### 完整产品业务边界

- RiskFlow 负责资料接入、知识建模、风险识别、风险评估、预警、处置建议、人工复核、反馈校准、追溯审计及对外接口，形成施工风险闭环。
- 文档管理、监测数据采集、CAD/BIM、施工进度管理和设备控制等既有系统属于外部系统；RiskFlow 通过文件导入、数据库连接、API 或专用适配器使用其数据，不重复建设外围平台。
- 完整产品面向多项目和多来源集成演进；MVP 只要求单项目及有限数据来源真实跑通。

### MVP 完成门槛

以下条件必须同时通过，任一项未通过时只能标记为开发中或技术就绪，不得宣称 MVP 完成：

1. 经确认的工程样例能够从资料接入运行至反馈校准，流程状态完整。
2. 每项结果均可追溯至资料段、工序节点、机理条目、规则版本和模型调用记录。
3. 风险评估与规则节点在相同输入、版本下结果一致；LLM 节点必须记录模型、参数、提示模板版本、检索证据和结构化输出，支持审计重放，不要求生成文本逐字一致。
4. 日常业务流程能够通过产品界面完成，权限、复核、版本和审计机制实际生效。
5. 系统能够在最低目标硬件上完成离线私有部署，并通过后续票据定义的质量、性能和工程样例验收指标。
