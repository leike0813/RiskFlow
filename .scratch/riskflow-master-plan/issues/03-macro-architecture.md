# 确定识别与评估一体化宏观架构

## Question

在双专利、四层架构、TypeScript 全栈、LangGraph 核心、完全私有化和可审计约束下，RiskFlow 应如何划分领域边界、部署单元、LangGraph 父子图、确定性领域服务与跨层契约，才能形成可演进且可交付的宏观架构？

## 已确认决策

### 部署形态

- 首期采用模块化单体，不按识别、评估、预警等业务能力拆分微服务。
- React 前端、Node.js API、Node.js LangGraph Worker 是可独立运行的部署进程；API 与 Worker 复用同一套 TypeScript 领域模块和契约。
- `llama.cpp` 是独立推理进程，通过模型网关接入，不构成第二套业务技术栈。
- 数据库、检索、图存储等基础设施的具体选型由后续数据与知识存储票据确定。

### 架构视图与领域边界

- 四层架构是强制依赖方向和双专利追踪视图，不直接对应四个部署服务。
- 业务按变化原因划分为六个领域模块：工程数据、知识建模、风险识别、风险评估、预警处置、复核审计。
- LangGraph 编排与 Agent 交互属于应用模块，只组织领域能力，不拥有或改写风险事实。
- 跨模块协作只能使用公开接口和版本化 DTO，禁止借助图节点跨层访问其它模块内部存储。

### LangGraph 运行模型

- 顶层 `riskFlowGraph` 根据业务触发原因选择可独立运行、可独立测试的 `identificationGraph` 与 `assessmentGraph`。
- 新资料进入时运行“识别 → 评估”；监测摘要、适用性元数据、适用规则集或风险矩阵版本变化时只触发重新评估。
- 预警和处置是 `assessmentGraph` 在风险评估记录可靠入库后的受控分支，不建立绕过评估事实的旁路。
- 每次业务触发创建有明确起止的运行；人工复核使用 LangGraph `interrupt/resume` 恢复原线程，不维护永久驻留、无限等待的图。
- 智能 Agent 工作台调用正式业务图并展示可审计步骤，不另建第二套业务状态机。

### 跨模块协作与一致性

- 同一运行内需要立即返回的领域行为通过 TypeScript 公开接口同步调用；模块之间不使用内部 REST 或 MCP。
- 已入库事实通过事务事件驱动后续任务，业务记录与待发布事件在同一事务中写入，消费方使用业务幂等键处理重复投递。
- LangGraph 检查点只保存编排状态、实体标识和版本引用；领域记录才是业务事实源。
- 具体数据库、事件设施和检索产品留给后续数据与知识存储票据决定。
