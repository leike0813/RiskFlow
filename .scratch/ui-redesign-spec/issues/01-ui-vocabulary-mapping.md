# 界面术语与甲方用语对照

Type: grilling
Status: resolved

## Question

界面要说工程业务的语言（`CONTEXT.md` 已定义「标准化风险记录」「风险评估记录」「预警处置任务」「处置建议」「处置反馈」「偏差记录」「校准建议」等），但甲方日常说的是另一套词（风险源清单、风险矩阵、指标体系、量化标准、措施库这些原始台账用语），而现有界面上跑的又是第三套（`runId`、监测快照 ID、发布集合、复核任务 ID）。

**哪些业务术语直接上界面、哪些需要甲方原始用语、哪些必须留在详情层不出现，以及同一概念在界面上叫什么** —— 需要逐个术语定下来，形成一张界面用语对照表。

具体要回答：

1. `CONTEXT.md` 的风险闭环术语里，哪些是**界面一级语言**（出现在导航、列表头、按钮、空状态里）？哪些只应出现在详情页的字段说明里？
2. 甲方原始台账用语与系统术语冲突的地方怎么办？例如甲方说「风险源」，系统说「标准化风险记录」，界面用哪个？是否需要建立一对多或按场景切换的关系？
3. 界面需要新增哪些 `CONTEXT.md` 里没有的词？新增词必须是工程业务语言，不能是实现术语（例如不能把「查询投影」当界面词）。若确需新增，当场写进 `CONTEXT.md`。
4. 一份可以交给甲方确认的界面用语清单长什么样？确认流程是否需要成为规格的一部分？

**不要**在这一票里决定页面怎么排、组件怎么做——那是别的票。

## Answer

产出资产：[界面用语对照表](../../riskflow-master-plan/prototypes/ui-vocabulary-mapping.md)。

同步修改：`CONTEXT.md` 新增「风险源」「风险因素」「风险事件」三个术语，各写明知识侧（甲方清单条目）与识别侧（模型输出字段）两层含义，并写 `_Avoid_` 互斥关系。

**关键事实**（决定了答案形状）：

1. **甲方原始清单文件不存在于仓库。** `docs/` 目录没有，`.scratch/` 只有规划 markdown。现存配置全部是合成的（`references/acceptance/synthetic-v1/`，`labelStatus=candidate`）。真正的"甲方输入清单"是待办文件 `待甲方输入与开发缺口.md:10-16`。所以对照表不可能照抄甲方列名，只能以两处高强度固化为准绳：`AGENTS.md:66` 业务规则七词表、专利七字段 → `packages/contracts/src/records/index.ts:26-41`。
2. **甲方用词已以中文枚举落进契约层**（`packages/contracts/src/vocabulary/index.ts`），零成本可上界面：工序节点 5 项、监测指标 6 项、风险机理类型 6 项、适用性维度 3 项、指标类型 2 项、指标组 5 项、预警触发类型 4 项。决定直接上界面，不另造显示名。
3. **导航层本来就干净**（`shell/navigation.ts` 七项全业务中文）。泄漏全在页面硬编码 JSX 串里，无集中词表、无 i18n。最狠四类：「标识」几乎全站且当成列头和手输表单标签；「快照」家族；「投影」；「游标」。`基线` 全域零命中，无需处理。
4. **21 个页面存在双标题不一致**（路由 `title` vs 页面 `<h1>`），其中 `/knowledge/measures` 路由写「指标库」而 h1 与 tab 都是「措施库」——路由标题是错的。

**定下的规则**：

- **权威关系**：`CONTEXT.md` 是领域术语唯一权威，界面用词是它的投影，不构成第二套术语。差异写进对照表，不两边各说一套。
- **三层分工**：业务对象层用 CONTEXT.md 术语（导航、列表头、按钮、空状态）；操作层用动词短语；证据层用甲方原词（指标名、量化标准、条款、评分），且甲方原词单独出现时必须带来源引用。
- **同形不同物**：知识侧叫「风险源清单」（甲方静态清单，对应 `风险机理库`），识别侧叫「风险记录」（运行事实），其内嵌三个字段显示为「风险源/风险因素/风险事件」。同一批词用页面语境区分。
- **四类泄漏处置**：① 删除（游标、投影、幂等键、JSON、Schema、Token，以及全部要求用户手输 ID 的表单标签）；② 换成业务词（工程修订→工程当前状态版本、发布集合→知识版本、快照家族→评估依据/监测数据范围、运行→任务、章节→资料目录/资料段）；③ ID 降为详情辅助（列头删除，详情页置灰等宽小字 + 复制；工程下拉显示名称而非 `projectId`）；④ 保留但改述（空态与错误句改成业务语气：说有什么、为什么没有、下一步做什么）。
- **代号词**：P/C 上界面并列为「发生可能性 P」「后果严重性 C」（专利固定词且甲方认可）；I0–I9 仅详情页作阶段码；JSON/Schema/Token 不出现；界面用「智能助手」而非「Agent」。
- **单一标题源**：路由 `title` 与 `<h1>` 必须一致，已列出 14 项需修正。
- **甲方确认**：不设独立确认关口，对照表作为规格一部分交付，甲方在验收时一次性审阅。

**遗留风险（须随规格一起交付）**：

1. 决定**普通业务页面不额外标注合成/待甲方确认状态**，但质量页面、试运行报告、验收记录及其导出或截图证据必须保留“合成样本，待甲方复核”、来源与候选资格。口头开场说明不能代替材料标注，也不能把合成配置证明的技术路径当作最终业务验收。来源误解风险仍保留。
2. 对照表以 grep 覆盖 `apps/web/src` 得来，未逐页通读 46 个页面组件，`WarningTaskPage` 关系标签、`PendingAssessmentPage` 列头等仍有同类残留。施工时按四类规则逐页套用并复查。
3. 未核 `openspec/specs/web/*` 是否已有术语规格；施工时若冲突，按 `AGENTS.md` §3 以代码为准并开 drift 修正 change。
