## Context

C30 的两条运行只读证明（精确绑定证明、运行完成证明）都经 `#latestRunStateWith` 读取运行状态行，该方法以 `parsedRow.authorizationScopeDigest === authorizationScopeDigest(input.verified)` 作为准入条件——**上下文摘要等值**。

已确认的现状事实（真实浏览器闭环取证）：一次人工以工程级范围启动的评估运行，其登记行摘要为 `ca04a2c3…`；C41 反馈路径按 C25 证明给出的单个空间签发读取上下文，摘要为 `00b8d34c…`。二者必然不等，于是完成证明读不到运行状态行，按 `completion-not-established` 关闭失败，`record-feedback` 永远走不通。

等值判定在真实部署里不可满足：人工以会话完整范围启动运行，模块按任务收窄范围读取，是正常的最小权限分工。把授权问题等同于身份摘要相等，使「我被授权读这条运行吗」变成「我的上下文和当初写它的那份一模一样吗」。

`authorizationScopeDigest` 本身没问题——它回答的是「这份事实是在哪份授权下形成的」，写入侧仍然需要它；问题只在于读取侧不该拿它当准入。

## Goals / Non-Goals

**Goals:**

- 运行只读证明按**授权覆盖**判定准入：调用方上下文的空间范围与来源授权覆盖运行已登记事实的范围即承认。
- 覆盖判定逐项集合包含，范围不足与跨工程仍稳定拒绝，且与事实缺失同型。
- 写入侧的授权范围摘要原样保留，审计与追溯不受影响。

**Non-Goals:**

- 不扩大任何调用方自身的签发范围；C41 仍按任务需要收窄。
- 不新增表、迁移、依赖或公共错误码。
- 不改动绑定证明与完成证明的既有核对项（工程、运行、评估记录、状态、run-result 一致性等）。
- 不把「运行由更宽范围启动」当作降低要求的理由：覆盖判定只回答授权问题，其余一致性核对一项不减。

## Decisions

### D-01：读取准入用覆盖判定，写入仍用摘要

`#latestRunStateWith` 的准入从等值改为：调用方上下文的 `spatialScopeRefs` 与 `sourceAccessGrantRefs` 各自**包含**运行已登记事实声明的范围集合，且 `projectId` 相同。

同一准入同时适用于完成证明读取的 `run-result` 行：两行同属一次运行的已登记事实，必须共用一个判定，否则状态行已承认、`run-result` 行仍按等值拒绝，完成证明永远无法成立。

- 理由：授权的真实问题是「你被允许看这条运行吗」，答案是覆盖而不是同一；摘要相等只是同一的充分条件，不是必要条件。
- 代价：判定需要知道运行声明了哪些范围。这些范围已存在于运行状态正文与登记行的 `authorizationScopeDigest` 输入集合中，但摘要本身不可逆——因此覆盖判定必须读取可比较的集合。
- 实测证据：闭环场景中该运行的 `run-state` 行写入摘要为 `204def30…`，反馈侧读取上下文摘要为 `cd762709…`；两者空间范围相同而来源授权与策略维度不同，按等值一律拒绝。

### D-02：覆盖判定以逐项集合包含表达，不用摘要近似

覆盖判定 MUST 基于可比较的引用集合逐项包含，MUST NOT 用摘要前缀、相近值、编辑距离或任何模糊匹配。

- 理由：任何「看起来像」的判定都会在授权上引入不可解释的容忍度。
- 代价：登记行需要能还原出当时的授权范围集合。

### D-03：范围来源取运行状态正文的已登记事实

覆盖判定比较的「运行范围」取自该运行状态与结果工件已登记的 C04 manifest 授权快照，分别包含空间、来源授权与策略引用。通过 C04 的既有公开读取接口执行覆盖校验，再读取正文核对运行事实；不从摘要反推、不读取 C04 私表、不在 retrieval 维护另一套空间判定。

- 理由：正文是已登记事实，摘要只是它的指纹；用正文判定才不会把指纹当事实。
- 考虑过的替代方案：从 `authorizationScopeDigest` 反推集合——不可行，摘要不可逆。

### D-04：不足与缺失同型失败

覆盖不足时与「运行不存在」返回同型失败，不返回部分事实、不枚举目标是否存在。

- 理由：避免通过失败形态探测目标存在性；与既有绑定证明的收口一致。

### D-05：其余一致性核对一项不减

工程、运行引用、状态为 `completed`、`assessmentRecordRefs` 含目标记录、`run-result` 行与正文一致等核对全部保留；覆盖判定只替换「能否读到这些行」这一个准入条件，且对 `run-state` 行与 `run-result` 行使用同一准入。覆盖不足一律以 `AUTHORIZATION_DENIED` 的「证明未成立」形态返回，不得伪装成事实不一致，也不得与事实核对共用失败码。

- 理由：这是授权口径的修正，不是把证明整体放宽；准入不成立与事实对不上是两件事，混用会让运维把授权问题误判成数据问题。

## Risks / Trade-offs

- **覆盖判定比等值宽松**：调用方只要持有覆盖运行范围的授权即可读该运行。这正是 C04 既有覆盖语义在同一工程内的既有行为，不引入新的授权模型；但确实放宽了 C30 读取面的准入，因此本 change 需要用户明确裁决。
- **登记行缺少可比较的范围集合**：若实现发现登记行无法还原写入时的授权范围，则须回到 D-01 的替代方案（要求调用方按运行原始范围签发），那会把问题推回调用方，需要重新裁决。

## Migration Plan

不涉及表结构与数据回填。历史登记行的摘要语义不变；判定只影响读取准入。

## Open Questions

无。覆盖判定的方向、集合口径、失败形态与不受影响的核对项已在上文定死；实施前需用户确认「授权需扩大」这一升级条件。
