# domain/warning-tasks-and-in-app-notification Specification

## Purpose
为 RiskFlow 把确定性评估触发事实可靠地收口为不可变预警、可持续归集的处置任务和应用内通知，并以独立确认事实表达人工已读接管，保持完整、幂等且可重放的 RA-S6 审计链。

## Requirements

### Requirement: 预警只能消费已持久化的确定性评估事实

系统 MUST 只按精确 `RiskAssessmentRecordRefV1` 读取 C25 已持久化的公共评估记录及其冻结输入上下文，并在任何目标读取前复验当前 C06 工程、空间和分支能力授权。系统 MUST 验证命令中的 `warningAggregationPolicyRef`、`notificationPolicyRef` 与该评估输入快照冻结的精确引用一致，再从正式运行时策略提供者取得同版本、同工程的 strict 策略；缺失、不相容、未获准或版本不匹配 MUST 失败闭合，不得选择“最新”策略、默认策略或内联替代值。（RA-S6）

C26 MUST 原样消费评估记录中的风险身份、空间身份、风险等级、四类 `triggerType`、触发指标和证据，不得重算或修改指标实际取值、P/C、风险矩阵、风险等级、风险接受阈值、监测阈值或联合触发结论。评估记录没有触发事实是合法结果，MUST 返回空的预警、任务和通知意图引用集合，不得伪造预警。（RA-S5、RA-S6）

#### Scenario: 由精确评估记录创建预警输入
- **WHEN** 获授权调用方提交一个属于目标工程和获准空间的精确评估记录引用，且两个策略引用与冻结评估输入及正式策略提供者完全一致
- **THEN** 系统只投影该记录已经保存的风险、空间、等级、触发指标和证据用于后续预警
- **AND** 不读取可变最新值或再次执行评估与触发算法

#### Scenario: 无触发事实返回空结果
- **WHEN** 精确评估记录包含完整评估结论但 `triggerIndicators` 为空
- **THEN** `open` 返回三个空引用集合并按既有命令幂等语义保存成功收据和审计
- **AND** 不创建预警、处置任务、通知意图或预警事件

#### Scenario: 策略或授权不匹配时失败闭合
- **WHEN** 调用方无权读取目标工程或空间，或者命令策略引用与评估快照、正式策略版本任一不匹配
- **THEN** 系统在创建预警、任务、通知意图、成功审计或事件前返回类型化失败
- **AND** 不泄露无权目标是否存在，也不使用默认、历史或其它工程策略继续

### Requirement: 每个评估与触发类型形成唯一不可变预警

系统 MUST 按公共四类 `WarningTriggerType` 对一个评估记录的触发指标规范分组；每个非空触发类型 MUST 形成且只形成一个公共 `WarningRecord`。预警 MUST 固定评估记录、当时风险等级、该类型规范排序去重后的触发指标、规范排序去重后的证据、正式策略给出的响应方向、`notificationStatus=intent-recorded` 及审计。预警记录创建后 MUST 不可修改；同一工程、评估记录精确版本与触发类型的重试或并发请求不得产生第二条预警。（RA-S6）

#### Scenario: 多类触发形成多条规范预警
- **WHEN** 一个评估记录同时包含风险等级越限、监测指标越限和联合规则命中的触发指标
- **THEN** 系统按三个触发类型分别创建三条预警，并在每条预警中只保留该类型的规范去重指标及其证据
- **AND** 所有预警继续引用同一精确评估事实，不合并或改写三类触发语义

#### Scenario: 同类重复指标只保留一次
- **WHEN** 评估记录中同一触发类型出现身份相同的重复触发指标或证据，且输入顺序不同
- **THEN** 预警按稳定身份规范排序并去重
- **AND** 相同冻结输入重放产生相同预警内容和精确引用

#### Scenario: 不同命令并发打开同一评估
- **WHEN** 两个不同命令同时处理同一工程、评估记录精确版本和触发类型
- **THEN** 数据库唯一性和同一事务边界只允许一条预警事实成立，两个调用均收口到规范预警引用或类型化可重试结果
- **AND** 不依赖进程内锁、缓存或另一套幂等登记表

### Requirement: 处置任务按工程风险与空间归集持续预警

系统 MUST 以工程标识、风险输入的 kind 与稳定实体标识、处置空间范围的稳定实体标识作为归集键。归集键下存在未关闭任务时，新预警 MUST 追加到该任务的新不可变版本；不存在未关闭任务时 MUST 创建新任务。一个 `open` 命令为同一归集键新增多类预警时 MUST 只形成一个结果任务版本，`warningResponseTaskRefs` MUST 去重；该版本完整关联本次及既有预警精确引用并保留各自触发类型、评估版本和空间版本。（RA-S6、RA-S7）

确认、通知成功或通知失败均 MUST NOT 关闭任务。已关闭任务不得因后续同键预警重新打开；后续预警 MUST 创建新的任务实体。任务关闭由后续已批准处置流程负责，C26 不新增关闭命令或根据风险等级自行推断关闭。（RA-S7）

#### Scenario: 持续越限归集到同一任务
- **WHEN** 同一工程、同一稳定风险和同一稳定空间在后续评估中再次产生预警，且既有处置任务仍未关闭
- **THEN** 系统创建该任务的新不可变版本并追加新预警精确引用
- **AND** 不创建第二个并行未关闭任务，也不覆盖先前任务版本

#### Scenario: 多触发类型共享一个任务版本
- **WHEN** 同一次 `open` 为同一评估创建多个触发类型的预警
- **THEN** 所有新预警归集到同一个结果任务版本，成功结果只返回一个该任务引用
- **AND** 每条预警仍保持独立触发类型和独立通知意图

#### Scenario: 已关闭任务不被重新使用
- **WHEN** 相同归集键的既有任务已经由后续正式流程关闭后又产生新预警
- **THEN** 系统创建新的处置任务实体并关联新预警
- **AND** 旧任务及其版本、确认和处置历史保持不变

### Requirement: 打开预警的事实与事件必须原子且幂等

系统 MUST 复用 C03 的 `(projectId, command kind, idempotencyKey)` 命令收据与载荷摘要，并在一个 PostgreSQL 事务中提交新预警、处置任务版本、应用内通知意图、C07 只追加审计、命令回执及每条新预警对应的 `warning.warning-recorded.v1` Outbox 事件。事件 MUST 使用对应任务精确引用作为聚合引用，并只携带公共契约规定的评估、预警、任务和通知意图引用；任何写入失败 MUST 整体回滚。（RA-S6）

同键同载荷重试 MUST 返回首次成功的三个规范引用集合且不重复任何事实；同键异载荷 MUST 返回 `IDEMPOTENCY_CONFLICT`。不同命令处理相同评估事实时仍 MUST 由预警与未关闭任务的业务唯一性收口，不得把命令收据扩展成第二套领域去重系统。

#### Scenario: 相同命令重试不重复预警
- **WHEN** 调用方以相同工程、`open` kind、幂等键和完全相同载荷重试成功命令
- **THEN** 系统返回首次提交的预警、任务和通知意图精确引用集合
- **AND** 不重复写入预警、任务版本、通知意图、审计或 Outbox 事件

#### Scenario: 同键异载荷被拒绝
- **WHEN** 调用方复用已完成的 `open` 幂等键但改变评估记录或任一策略引用
- **THEN** 系统返回 `IDEMPOTENCY_CONFLICT`
- **AND** 首次结果和全部既有事实保持不变

#### Scenario: 原子写入失败整体回滚
- **WHEN** 预警、任务、通知意图、审计、命令回执或 Outbox 任一步写入失败
- **THEN** 本次命令的全部新写入均不可见
- **AND** 调用方可以沿用原幂等身份安全重试

### Requirement: 应用内通知投递不得影响预警事实

每条新预警 MUST 按其精确正式通知策略为每个获准接收人创建唯一、不可变且 channel 固定为 `in-app` 的通知意图，并与预警、任务、策略版本和审计同事务保存。通知策略未解析到至少一个合法接收人时 MUST 在预警事务提交前失败闭合；调用方不得在命令中覆盖接收人、渠道或通知内容，也不得使用未经审核的默认策略。（RA-S6）

Worker MUST 只在 `warning.warning-recorded.v1` 已可靠入库后消费其通知意图，并复用 C03 PostgreSQL 幂等消费者，在独立事务中创建应用内通知投递事实。重复事件、租约恢复或进程重启 MUST 最多形成一份同意图同接收人的投递事实。投递失败 MUST 由既有 Outbox 重试和失败记录收口，不得删除、回滚、改写预警、任务、通知意图或成功的打开命令，也不得把投递状态解释为人工确认。

#### Scenario: 预警提交后投递应用内通知
- **WHEN** 一条带合法应用内通知意图的预警事务已经提交，Worker 收到对应预警事件
- **THEN** Worker 在独立事务中为每个意图创建一次应用内通知投递事实
- **AND** 投递事实保留预警、任务、接收人和通知策略精确引用

#### Scenario: 通知失败不回滚预警
- **WHEN** 预警事实已经提交但应用内通知写入暂时失败
- **THEN** 已提交的预警、任务、通知意图、审计和打开命令结果保持可见且内容不变
- **AND** 既有 Outbox 机制记录失败并重试，不伪造已送达或已确认状态

#### Scenario: 重复事件不重复通知
- **WHEN** 同一 `warning.warning-recorded.v1` 因至少一次投递、租约恢复或 Worker 重启被重复消费
- **THEN** C03 幂等消费者与通知投递唯一性只保留一份同意图同接收人的应用内投递事实
- **AND** 不增加第二套消费者收据、业务缓存或进程内去重

### Requirement: 确认只记录已读接管并保持精确配对

系统 MUST 实现公共 `WarningResponsePortV1.record` 的 `acknowledge` 分支，并严格沿用已归档契约的 payload、成功结果、`warning-response.record` 能力和 `warning.warning-acknowledged.v1` 事件。确认前 MUST 先复验当前 C06 授权，再联合验证预警与处置任务属于同一获准工程和空间、任务精确版本归集该预警精确版本且仍可确认。一次任务归集多个预警时，每个预警与任务配对 MUST 分别确认。（RA-S6、RA-S7）

确认 MUST 只追加首次确认操作者、时间、预警与任务精确引用及审计；它不修改预警、评估或通知事实，不改变风险等级和触发状态，不关闭任务，也不产生建议采纳、执行、反馈、偏差、校准或风险解除结果。确认事实、C07 审计、命令回执和 `warning.warning-acknowledged.v1` Outbox 事件 MUST 在同一事务成立。

#### Scenario: 获授权管理员确认一条预警
- **WHEN** 工程风险管理员以具备 `warning-response.record` 能力的当前授权提交相互关联且仍可确认的预警与任务精确引用
- **THEN** 系统返回 `kind=acknowledgement`、`status=acknowledged` 及同一引用配对
- **AND** 原子保存确认事实、审计、命令回执和确认事件

#### Scenario: 确认不表示风险解除
- **WHEN** 一条预警被成功确认
- **THEN** 预警、评估、风险等级、触发依据、任务打开状态和通知投递状态均保持原有事实
- **AND** 后续解除、关闭、采纳、执行和反馈仍须经过各自正式流程

#### Scenario: 不匹配或陈旧任务版本被拒绝
- **WHEN** 任务未归集目标预警，或者命令引用的任务精确版本已被后续预警归集推进
- **THEN** 已获权且目标可见的调用方收到类型化业务阻塞或 `STALE_VERSION`
- **AND** 无权、跨工程、跨空间或不可见目标使用不可枚举拒绝且不产生副作用

#### Scenario: 确认重试和并发接管保持唯一
- **WHEN** 相同确认命令重试，或者多个不同命令竞争确认同一尚未确认的精确配对
- **THEN** 同键同载荷返回首次结果，同键异载荷返回 `IDEMPOTENCY_CONFLICT`，不同命令仅一个建立确认，其余返回类型化业务冲突或陈旧版本
- **AND** 不覆盖首次确认操作者，不重复审计或事件

### Requirement: 预警链路必须可重放且最小披露

系统 MUST 使每条预警可沿精确引用追溯到评估记录、风险输入、适用性与空间快照、触发指标、证据、规则/权重/矩阵版本、归集策略、处置任务版本、通知策略与意图、应用内投递、确认事实和 C07 审计。历史版本 MUST 只追加且可按当时冻结输入重放；后续策略、评估、任务或投递变化不得改写既有链路。（RA-S5、RA-S6、RA-S7）

普通结果、事件、日志和错误 MUST 只披露获准的稳定标识、精确引用、结果类别和稳定原因码，不得复制评估正文、证据正文、通知内容、接收人私有信息、授权详情或数据库错误。审计失败 MUST 使所属业务事务失败；异步通知失败只影响独立投递事务。

#### Scenario: 标准风险链可确定性验收
- **WHEN** G2.5 验收夹具以一个正式 `RiskInputRef` 完成评估并产生触发事实，再执行预警打开与确认
- **THEN** 可从风险输入经 P/C、矩阵、触发、评估记录追溯到预警、唯一处置任务、通知意图、应用内投递、确认和审计
- **AND** 重放打开命令及预警事件不产生重复业务事实

#### Scenario: 历史链不受后续版本影响
- **WHEN** 归集或通知策略、评估记录、任务版本或授权随后发生变化
- **THEN** 既有预警继续引用创建时的精确输入、策略、任务和通知意图
- **AND** 不以当前版本覆盖历史记录或改变历史确认含义

#### Scenario: 错误和事件保持最小披露
- **WHEN** 预警打开、确认或通知投递失败
- **THEN** 普通错误、事件与日志不包含评估正文、证据正文、通知正文、接收人私有信息或底层数据库错误
- **AND** 受保护审计仍保留定位和重放所需的精确引用与稳定原因
