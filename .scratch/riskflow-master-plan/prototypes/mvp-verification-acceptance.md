# RiskFlow MVP 测试、验收与交付证据——待复核推荐记录

> 状态：Wayfinder 已确认的规划基线；本文不替代后续 OpenSpec 正式规格。

## 1. 验收结论与责任

### 问题 1：测试结果、技术就绪和 MVP 验收是否使用同一个“通过”状态？

可选方向：

- 所有检查通过后统一称为“MVP 验收通过”；
- 区分单项结果、技术就绪和甲方验收三个层级；
- 只输出测试报告，不定义里程碑状态。

**推荐默认：分成三个层级，禁止用技术就绪冒充 MVP 验收。**

暂定结论：

1. 单个测试或验收项只使用“通过 / 不通过 / 阻塞”三种结果；阻塞不得折算为通过。
2. 冻结评测包、系统测试、目标硬件部署和交付包检查全部通过后，状态为“技术就绪”。
3. 甲方验收包在目标内网环境完成见证运行、语义结果复核和交付物核对，并形成书面确认后，才可标记“MVP 验收通过”。
4. 甲方资料或阈值未到位时，相关项记为“阻塞：待甲方输入”，系统最高只能达到“技术就绪”。

### 问题 2：谁编制证据、谁复核业务结果、谁作最终验收决定？

可选方向：

- 乙方自行测试并宣布通过；
- 甲方负责全部测试和结果判断；
- 乙方负责方案与证据，领域复核人确认语义结果，甲方作最终验收决定。

**推荐默认：乙方举证、领域复核、甲方最终确认。**

暂定结论：乙方负责编制测试计划、冻结环境、执行验证、修复缺陷并形成证据；领域复核人对甲方验收包中的风险识别、规则适用、处置建议和证据支持逐项确认；甲方核对业务样例、验收范围和交付物后签署最终结论。系统自动报告或模型自评均不能代替人工验收决定。

### 问题 3：是否用总分或“多数通过”决定 MVP？

可选方向：

- 将全部指标加权成总分；
- 允许少量关键项失败，由其它高分抵消；
- 使用分层硬门槛，任一必选门槛失败即不通过。

**推荐默认：沿用质量评测票的分层硬门槛，不设综合总分。**

暂定结论：专利追踪、契约、权限、安全、证据、审计、确定性计算、离线部署、甲方样例闭环和交付完整性均是一票否决项。语义质量采用已确认的指标门槛与人工判断。非关键缺陷可以带条件关闭，但不能掩盖关键切片失败。

## 2. 冻结基线与证据组织

### 问题 4：一次可审计的验收运行需要冻结什么？

可选方向：

- 只记录软件版本和测试日期；
- 冻结代码、环境、数据、模型、知识、规则、评测器和门槛的完整组合；
- 允许测试过程中更新规则或阈值，只保留最终状态。

**推荐默认：每次验收运行使用完整、不可变的验收基线。**

暂定结论：每次验收运行至少固定并记录：软件发布版和源码提交、数据库迁移、容器/离线制品摘要、主机与虚拟机配置、驱动与 CUDA、`llama.cpp` 构建、模型与 Embedding 文件哈希、解析器与 OCR 版本、数据包、知识发布集合、提示模板、Agent 工具策略与预算、适用规则集、权重、矩阵、两类阈值、措施库、评测器、门槛和操作人。运行中任何实质变更都必须创建新的验收运行，不得覆盖原结果。

### 问题 5：需求、测试与证据如何对应？

可选方向：

- 在报告中自由描述覆盖情况；
- 只做 RI-S1～RI-S6、RA-S1～RA-S7 的高层勾选；
- 建立可机器读取的双向追踪矩阵。

**推荐默认：建立“需求 → 验收项 → 运行结果 → 原始证据”的双向追踪矩阵。**

暂定结论：矩阵至少覆盖 `AGENTS.md` 的 RI/RA 子步骤、字段契约、领域枚举、Agent-native 横切约束、已确认功能用例、界面验收要点和部署治理边界。每个验收项必须有稳定标识、前置条件、输入版本、预期可观察结果、执行方式、结果和证据引用；每个证据也必须能反查所支持的验收项。必选要求无证据即失败，截图或口头说明不能单独证明后端事实成立。

### 问题 6：开发集、冻结评测包和甲方验收包如何进入系统验收？

可选方向：

- 三类数据混合使用；
- 直接沿用“确定模型、检索与规则质量评测策略”的三层隔离；
- 系统验收另建第四套重复数据体系。

**推荐默认：直接复用既有三层数据契约，不创建重复事实源。**

暂定结论：开发集用于开发与自动化回归；冻结评测包用于质量门禁、故障场景和专利最小覆盖；甲方验收包用于最终业务验收。三者继续按来源家族隔离。系统验收只编排这些数据包与正式业务接口，不复制金标准、P/C、矩阵、规则或质量指标实现。

### 问题 7：甲方正式风险清单、指标、矩阵或样例未到位时怎么办？

可选方向：

- 使用编制数值完成验收并视为正式业务正确；
- 停止全部开发和测试；
- 使用同形合成配置证明技术路径，同时建立缺口清单并保留最终阻塞。

**推荐默认：允许同形合成配置证明技术就绪，最终业务验收保持阻塞。**

暂定结论：合成包必须明确标注来源、适用范围和不可代表甲方业务结论；不得出现“甲方已确认阈值”等误导表述。缺口清单逐项记录所需输入、责任方、用途、最晚到位点和受阻验收项。正式输入到位后创建新版本并完整重跑受影响的确定性、质量与端到端验收，不在原报告上改字。

## 3. 工程检查、契约与确定性逻辑

### 问题 8：自动化测试采用什么层次，怎样避免测试本身膨胀？

可选方向：

- 追求高覆盖率并为每个函数写测试；
- 只做浏览器端到端测试；
- 按稳定行为选择最小测试层次，复用已确定的工具链。

**推荐默认：少量高价值分层测试，不设覆盖率数字目标。**

暂定结论：

- `tsc -b`、ESLint、Prettier 检查和 dependency-cruiser 作为每个候选发布版的基础门禁；
- Vitest 验证领域 Schema、版本语义、P/C、矩阵、阈值、幂等和权限等稳定行为；相似规则使用表格驱动；
- Testcontainers 验证 PostgreSQL、Qdrant、Outbox 与 LangGraph checkpointer 的真实适配器语义；
- React Testing Library 只验证用户可观察的交互与权限状态；
- Playwright Chromium 只覆盖关键业务闭环和少量高风险失败路径。

不新增为覆盖率服务的低价值测试，不精确断言完整文案、HTML/CSS 细节、内部调用顺序或大段快照。

### 问题 9：共享 Schema 与接口契约的验收门槛是什么？

可选方向：

- 只检查 TypeScript 能编译；
- 对关键接口做几个示例；
- 对共享 Zod Schema、版本字段、联合类型和边界适配执行 100% 契约验证。

**推荐默认：所有业务边界以共享 Zod Schema 为硬门槛。**

暂定结论：Web、API、Worker、领域事件、持久化记录、LangGraph DTO、Agent 增量和评测报告均引用同一契约事实源。标准化风险记录及 §2.7 各类记录的字段、必填性、枚举、`schemaVersion` 和精确版本引用必须 100% 正确；`riskRecordId` / `externalRiskEventId` 的二选一且仅一个必须在类型与运行时同时验证。非法载荷应形成结构化失败，不得部分入库或产生空成功。

### 问题 10：P/C、矩阵、阈值与规则适配怎样验收？

可选方向：

- 抽样几个常见结果；
- 使用总体准确率；
- 对生效配置空间、边界和异常分支要求精确一致。

**推荐默认：沿用质量评测票的 100% 确定性门槛。**

暂定结论：覆盖资料字段/监测摘要映射、单位换算、分值区间、权重聚合、舍入、风险矩阵每个生效单元、风险可接受阈值、监测预警阈值、四类预警触发、规则冲突、适用性筛除、缺失值和单位不兼容。相同冻结输入与版本重复执行时，结果、引用和审计决定必须精确一致；任何数值容差都只能来自版本化公式。

### 问题 11：基础设施适配器应验证哪些真实语义？

可选方向：

- 用内存 Mock 证明调用成功；
- 只在最终部署时人工观察；
- 对最容易产生数据错乱的边界使用真实服务集成测试。

**推荐默认：只对关键持久化边界做真实服务集成测试。**

暂定结论：至少验证领域事实、审计和 Outbox 同事务；Outbox 至少一次投递下的幂等；检查点与业务入库分离；索引版本对账、双索引就绪与 PostgreSQL 回查；图谱和 Qdrant 投影可删除重建；文件先耐久落位后提交引用；无数据库悬空文件引用；监测批次更正与迟到数据只追加。无需为普通纯函数启动容器。

## 4. 端到端、界面、权限与 Agent

### 问题 12：端到端验收需要覆盖多少路径？

可选方向：

- 只跑一条顺利的汇报主线；
- 把所有组合都放进浏览器测试；
- 浏览器验证一条完整主线与少量关键分支，其余在契约和集成层验证。

**推荐默认：一条完整闭环加七类高风险分支。**

暂定结论：主线必须从工程开通、资料与监测接入、知识/规则发布、识别、复核、评估、预警、处置、反馈、偏差、校准建议、人工确认和新版本发布一直运行到追溯与导出。高风险分支至少覆盖：资料不可用、规则冲突或不适用、证据/字段不完整进入复核、权限拒绝、必经 Agent 失败或预算耗尽、预警通知失败但事实保留、监测/规则版本变化触发重新评估。浏览器只验证用户操作与关键结果，细分边界由较低层测试承担。

### 问题 13：界面验收按页面像素还是业务可操作性？

可选方向：

- 对照截图逐像素验收；
- 只看页面能打开；
- 按完整界面规格的可观察行为和一致状态验收。

**推荐默认：以业务可操作性、状态一致性和可访问基础为准。**

暂定结论：逐项验证七项业务导航、五类页面骨架、空/加载/异常/权限状态、证据抽屉、高影响命令确认、识别一站式复核、两类阈值区分、预警确认语义、处置三项校验不可绕过、校准无立即生效入口、Agent 停靠栏与全屏工作台。日常闭环必须全程可由界面完成；不锁定完整文案、像素或 DOM 结构。键盘可达、表单标签、焦点、颜色不作为唯一信息载体和错误提示关联属于硬性可访问基础。

### 问题 14：权限与安全验证的重点是什么？

可选方向：

- 只测试登录成功；
- 只检查前端按钮是否隐藏；
- 从服务端授权、资料权限、会话、秘密和审计五个边界验证。

**推荐默认：所有越权路径都由服务端拒绝，前端状态只作用户体验。**

暂定结论：角色能力、工程成员授权和资料访问范围按交集验证；系统管理员不自动获得工程业务权限；业务查看者不能写入；Agent 不扩大当前用户权限；无原件权限者可看获准结论与定位但不能读取正文或导出原件。还需验证本地账号创建/停用/重置、密码强哈希、会话超时与强制失效、CSRF/输入边界、上传类型与大小限制、日志/导出不泄露秘密、凭据不进入源码/镜像/模板/SBOM/日志。每次拒绝和敏感读取均产生适当审计。

### 问题 15：Agent-native 运行怎样进入 MVP 验收？

可选方向：

- 只检查 Agent 能回答问题；
- 五类任务共用一个成功率；
- 共用治理硬门槛，分别验证五类任务的业务价值和失败路径。

**推荐默认：完整复用 Agent-native 契约与质量票门槛。**

暂定结论：五类必经内嵌任务和交互任务必须验证输入冻结、工具白名单、权限交集、硬预算、模型/提示版本、工具行动、类型化增量、确定性接受/拒绝、候选版本、失败和正式结果引用。越权、超预算、静默换模型/策略、跳过必经任务、改变 P/C/矩阵/阈值、发布业务定义、保存或展示思维链均为零容忍。交互式写命令必须等待用户确认。

### 问题 16：追溯与审计应以页面展示还是底层证据为准？

可选方向：

- 页面能显示一条链即可；
- 只检查数据库里有审计行；
- 同时验证领域引用、审计事件、权限控制和导出证据。

**推荐默认：端到端链条与底层引用必须逐级对账。**

暂定结论：从任一标准化风险记录、风险评估记录、预警信息或处置任务都能回溯“资料段标识 → 工序节点 → 风险机理条目 → 标准化风险记录 → 风险评估记录 → 预警信息 → 处置建议 → 偏差记录 / 校准建议”，并继续查看模型/提示、检索、规则/权重/矩阵、复核和操作者版本。抽查页面、API、PostgreSQL 事实和导出包四处引用一致；无资料权限时不泄露正文。审计只追加，普通应用角色不能修改或删除。

### 问题 17：失败、重试、暂停和恢复怎样验证？

可选方向：

- 只测试成功流程；
- 人工终止进程后确认能重新运行；
- 对每类长流程设置可重复的故障注入和幂等断言。

**推荐默认：验证少量代表性故障，重点检查不丢事实、不重复副作用。**

暂定结论：至少对解析、索引投影、模型调用、Agent 任务、人工复核暂停、预警通知和外部结果同步各选一个代表性失败点。验证策略内重试、预算耗尽终止、检查点恢复、重复恢复、Outbox 重投和用户显式重启均不会重复生成业务事实、通知或发布决定；已可靠入库的上游事实不回滚；不可修复冲突不能靠循环重试绕过。

## 5. 恢复、部署与性能

### 问题 18：MVP 的“恢复验收”是否意味着生产级备份和灾难恢复？

可选方向：

- 按早期存储方案验收 PITR、RPO/RTO 和周期性恢复演练；
- 完全不做恢复验证；
- 以后续私有化治理边界为准，只验证同机逻辑恢复与发布回退。

**推荐默认：只验证承诺范围内的逻辑恢复，不宣称灾备。**

暂定结论：MVP 必验应用/Worker/模型进程重启、LangGraph 暂停恢复、事务与 Outbox 幂等、Qdrant 和图谱从 PostgreSQL 重建、同机部署快照或发布包回退后的完整性核查。记录恢复步骤、耗时和数据核对结果，但不形成生产级 RPO/RTO 承诺。独立冷备只有采购后才增加“人工全量同步、启动一次、恢复至最近同步点”的附加验收项。

### 问题 19：离线私有部署怎样判定通过？

可选方向：

- 开发机能运行即可；
- 在甲方服务器手工启动一次；
- 用冻结离线制品在目标三虚拟机拓扑上重复执行安装、启动、升级和回退。

**推荐默认：目标内网无公网条件下完成可重复部署。**

暂定结论：验证推理、应用、数据三虚拟机的网络与端口隔离；仅应用 HTTPS 对业务用户开放；数据库、Qdrant 和模型端口不对普通网段暴露；断开公网后仍可安装、启动、运行完整样例、查看审计和导出。交付前至少从干净目标环境执行一次部署，并对候选升级包执行一次升级与回退；所有依赖使用精确锁文件、镜像 digest、离线缓存和工件哈希，不在验收现场临时联网下载。

### 问题 20：哪些性能指标现在设硬门槛，哪些留给目标硬件实测？

可选方向：

- 现在为所有阶段拍脑袋给出绝对耗时；
- 完全不设性能门槛；
- 对稳定短操作设置门槛，对模型、解析和全链路先实测再冻结验收包络。

**推荐默认：分两类管理。**

暂定结论：

- 已确认的检索门槛保持冻结 MVP 语料、单查询 p95 ≤ 2 秒；
- 代表性非长任务页面/API 查询 p95 ≤ 2 秒，长任务创建并返回运行标识 p95 ≤ 2 秒，运行状态首次可见或后续更新间隔不超过 5 秒；
- 文件解析、索引构建、模型/Agent、完整识别和完整闭环不在缺少实机数据时虚构绝对耗时。它们先在目标硬件和冻结负载上记录 p50/p95、吞吐、错误率、排队、峰值 CPU/RAM/VRAM/磁盘及热稳定性，再由性能验收配置冻结甲方可接受上限，最终验收按该版本执行；
- MVP 只承诺单项目、模型单并发槽。多项目规模和并发 2 只报告实验结果，不作为首发承诺。

### 问题 21：模型与目标硬件基准如何执行？

可选方向：

- 采用网上 tokens/s 数据；
- 只确认模型能加载；
- 在实际 RTX 4090 + 128GB 环境冻结配置并做质量、性能、资源和稳定性联合基准。

**推荐默认：使用已确认的 Qwen3.8-27B 基线候选做实机联合验收。**

暂定结论：首个必须验证的配置为 `Qwen3.8-27B Q4_K_M`、文本、`parallel=1`、32K 总上下文、F16 KV、关闭 MTP；固定 GGUF、`llama.cpp`、CUDA/驱动和全部参数。至少记录冷启动一次、代表性请求不少于 30 次、三次完整语义评测运行和一次持续负载观察；报告 TTFT、prompt/decode timings、端到端 p50/p95、错误/超时、峰值资源和输出质量。32K 未通过时不得静默降低上下文冒充基线，应回到验收配置复核；64K、并发 2、视觉、KV 量化和 MTP 只作独立实验。性能改善不能交换质量、安全或证据门槛。

### 问题 24：缺陷如何分级，什么情况下可以带条件验收？

可选方向：

- 只区分“有 bug / 无 bug”；
- 所有缺陷都阻塞；
- 按是否影响事实正确性、安全、闭环或非关键体验分级。

**推荐默认：三级缺陷，关键缺陷零遗留。**

暂定结论：

- **阻断缺陷**：数据丢失或覆盖、错误 P/C/等级/预警、越权或秘密泄露、证据/审计断链、Agent 绕过约束、无法离线部署、甲方样例闭环中断；必须修复并重跑受影响验收项。
- **主要缺陷**：关键功能可绕行但明显影响业务使用、结果解释、性能包络或恢复；默认阻塞技术就绪，只有甲乙双方明确接受替代路径、期限和责任时才可带条件关闭。
- **一般缺陷**：不影响事实、安全、闭环和核心可操作性的局部体验问题；可进入已知问题清单，不阻塞验收。

任何缺陷关闭都必须关联修复版本和回归证据，不能只改状态。

## 7. 交付物与移交

### 问题 25：完整交付包应包含哪些类别？

- 交付可重建源码、可离线部署制品、受治理业务资产、证据与手册的完整集合。

**推荐默认：按六类交付，并用清单统一校验。**

暂定结论：

1. **软件**：源代码、精确锁文件、数据库迁移、构建脚本、配置模板和版本说明；

## 8. 推荐结论摘要

- 单项结果、技术就绪和 MVP 验收分层管理；没有甲方认可样例与书面确认，不能宣布 MVP 通过。
- 不设综合总分；专利、契约、权限、安全、证据、确定性计算、离线部署和完整闭环均为硬门槛。
- 每次验收冻结软件、环境、数据、模型、知识、规则、策略、评测器和门槛的完整组合，并建立双向证据矩阵。
- 自动化测试保持少而稳：共享契约与确定性逻辑用 Vitest，真实数据边界用 Testcontainers，关键用户闭环用少量 Playwright。
- 主线真实走通 RI-S1～RI-S6、RA-S1～RA-S7；关键失败、权限、Agent、重评估和通知失败路径不得静默绕过。
- 恢复验收以后续治理边界为准，只验证同机逻辑恢复、幂等续跑、投影重建和发布回退，不宣称灾备。
- 检索 p95 与普通交互设置明确门槛；模型、解析和完整闭环先在目标硬件实测，再冻结可接受包络。
- 模型质量完全复用已确认的质量评测策略；甲方验收包语义输出全检，确定性结果自动精确对账。
- 交付覆盖软件、离线制品、模型/检索、知识与配置、质量证据和移交资料，并由带哈希的单一清单索引。
- 本票关闭后不新增重复 Wayfinder 决策，下一张“确定覆盖 MVP 的 OpenSpec 实现路线”承接实施拆分。
