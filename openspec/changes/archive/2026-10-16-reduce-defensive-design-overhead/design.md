## Context

当前 HEAD 为 `31ad1a2c47a377f20179e0008241034c14a3bec5`，功能验收实现大量位于未提交叠加层；HEAD 本身不是现场实现检查点。规划以审计报告、已归档主规格、当前实际代码及已确认业务决定为依据，按 `implementation-plan.md` 固定施工范围。原验收任务为5/19，已有资料、知识和识别阶段结果继续有效。

系统没有第三方业务调用方。HTTP、模型输出、资料导入是实际输入入口；同一动作中的内部模块属于可信实现。当前 `AuthorizationContextV1` 可继续作为一次访问决定与审计快照，不能再作为每过一层都要重新签发的凭据。

## Goals / Non-Goals

**Goals:** 删除逐层授权、只读命令幂等、检索授权全等、检查点递归举证、文件重复验真及无业务意义的重复审批；使既定界面能够完成原业务链，保留结果正确性和现有差异权限。

**Non-Goals:** 不重设计评分算法、知识语义、界面视觉和 C38 硬件交付；不操作现场服务和数据库，不运行现场模型或迁移，不安装依赖、提交或归档。当前进入已批准方案的代码实施与隔离测试阶段。

## Decisions

### D-01 使用场景与删除标准

采用可信人员通过交付界面使用封闭系统的前提。业务入口负责当前权限、输入和状态，专业模块负责单位、适用性、评分及三项处置约束；可信内部调用直接使用结果。人工改库、替换存储文件和伪造模块调用不作为日常运行场景。保留参数化数据库访问、安全文件目录、惰性原件展示、凭据隔离等现有基础能力。

删除没有业务入口的任意改写能力及其附属防护；不新增“宽松模式”开关，也不长期保留两套运行机制。保留原复杂体系再逐项放行不能消除维护负担，因此不采用。

### D-02 当前权限只在业务动作入口检查

复用 C06 账号、成员、空间、资料授权事实及 `AuthorizationContextV1` 审计结构，在 `packages/core/src/access/authorization.ts` 声明业务动作授权输入；由现有 C06 adapter 实现 `authorizeBusinessAction`。输入为可信 `actorId`、`projectId`、业务 `capability`、所需空间与来源版本，以及可选已登记任务/因果运行引用；调用编号用于日志关联，不作为授权有效性配对条件。HTTP 从会话确定 actor，后台从任务/发布事件的持久来源取得 actor，客户端和模型不提交权限决定。

一次业务动作在所属模块解析目标元数据后、披露正文前检查当前权限。异步模型/工具完成后的正式结果提交是新的动作，按结果全部来源再检查一次。内部通过原 `AuthorizationContextV1` 传递同一决定；不引入签名票据或另一套持久上下文表。移除组合根 `issuedInvocations`、`invocationKey`、逻辑/实际调用翻译，以及 `authorizeDownstream`/`issueReadContext` 的逐调用签发职责；现有 causal authorization 行仅供历史读取，不再作为执行前提。

后台任务冻结来源是上界，入口以当前权限与上界求交。网页注销或到期不停止后台；账号停用、成员移除或资料撤权在下一次读取或提交生效。租约、取消及预算由原 C08/Worker 负责，C06 不再回查 Worker 租约来签发五分钟行动凭据。实际业务权限仍按领域动作检查，不能把 `workflow.resume` 当成任意领域写权。

已登记任务通过 C08 的 `registeredTaskReader` 取得主体和冻结范围。业务动作输入可携带原 `authorizationContextRef`，仅复用同主体、工程和能力的审计快照；当前权限仍从当前事实计算，不因复用而新增上下文行或改写原记录。空间及资料限制按其业务身份使用当前修订，旧工件保存的历史权限修订只用于追溯。

### D-03 普通读取与业务提交分开

业务命令收据插入遇到任一既有唯一约束冲突后，按原(projectId, commandKind, idempotencyKey)锁定回读并比较payload；无对应收据或payload不同仍拒绝。同键并发不因另一个command_id唯一索引先报告冲突而失去正常重放，原事务与数据库唯一约束保持。

`PostgresArtifactRegistry.recordAccessOutcome` 采用自己的短事务直接插入访问记录和对应只追加审计，不经过 `TransactionUnit.execute` 的命令去重。每次实际访问生成一个 UUID 作为 `request_id`，生命周期内 authorized/succeeded/cancelled/failed 共用该 ID；`queryId`/任务ID作为关联信息，不再充当唯一读取身份。现有表和唯一键可复用，不改写旧行。

纯读取 C15 准备、C08 失败证据及类似已有对象的 reader 同样只记录访问，不插入业务 `command_receipts`。会物化正式检索、投影或导出结果的操作仍是写入：保留稳定业务输入去重；当前访问时间、授权记录ID和临时调用ID不参与业务内容摘要。业务写入、审计、回执和 Outbox 的原事务边界保留。审计失败如实报错，不静默丢弃。

### D-04 文件写入确定身份，普通读取直接消费

`ArtifactStoreV1.put` 继续计算 SHA-256、耐久落位和登记，保留写入去重。`open` 按登记清单定位受控目录，保留普通文件/目录限制、流式背压、大小、并发、取消和独立字节块；删除清单摘要回读及读取流全文哈希。

将普通读取句柄的 `verified` 改为含义明确的 `completed`，表示到达 EOF 且成功记录终态，所有本地/远程适配器、原件读取和消费方同批更新。`verifyContent` 的业务正文验证移至实际消费者的有界解析；独立维护/备份恢复的显式哈希核对保留，日常模型父工件预检取消全文遍历，只解析已登记来源限制。模型同步响应保存后直接解析同次读取的有限字节，不再次打开文件证明保存成功。

旧工件引用及清单继续使用，不搬迁或重命名对象。备份仍保护用户资料；损坏注入测试属于独立运维核验，不作为本次正常业务链的通过条件。

### D-05 知识索引固定内容，查询筛选可见成员

代际选择键继续使用工程、知识发布、检索策略和向量/BM25配置；从 `readActiveGeneration` 与冻结检索输入中移除调用者完整 `authorizationScopeDigest` 全等前置。旧代际行的历史摘要继续可读但不参与选择。

统一入口从已登记成员及其来源限制取得当前账号可见的成员ID集合，两路召回使用同一集合过滤，之后再融合 Top-K；不能先对全库 Top-K 再去掉不可见项。Qdrant 仅作为投影，命中内容仍从原知识事实读取。无可见成员返回合法空检索；补搜仍只在任务冻结范围内。

C17在发布事务内登记三类检索条目的原批准正文、精确发布与来源引用，作为原知识包的条目读取面；不把Qdrant载荷作为正文事实。唯一000059迁移增加条目登记表。旧发布由原包在受信投影构建入口补登记，不重新审核或改变发布引用。C06提供批量可见来源读取，复用账号、工程成员、资料可见性与任务范围判断；C17只返回全部证据来源均可见的条目。查询从这些条目计算原pointId，两路prefetch按同一has_id范围过滤，去重记录实际成员集合。

物化结果记录本次实际成员范围及内容代际，不记录“所有授权必须相等”的证明；查询去重依赖这些业务输入。新增无关监测资料不触发重新发布或建库。原代际无需因为授权减负而重算向量；仅投影缺少必要成员标识时按原发布重建投影，不改变内容或质量阈值。

### D-06 检查点只管理进度

保留原官方 PostgresSaver、独立角色和小型状态 Schema，删除 `collectContractReferences`、递归 `validateReferences` 以及组合根逐类型正文证明分派。图状态的工程、运行、线程和图版本在保存或恢复入口核对；官方 envelope、channel versions、counters 等由当前库处理，不自行复制其全字段白名单。

业务阶段提交仍由原模块登记。恢复在实际推进前使用已登记运行游标和对应阶段结果，恢复 I6 的 `mergePlanRef` 等必需增量；只读取下一步需要的结果，不遍历历史全部引用。业务领先检查点时继续原运行，缺少必需结果则明确报错，终态和取消状态不被覆盖。错误详情读取按真实错误引用定位，不因保存检查点而证明全部错误正文。父运行引用子运行已保存的错误，不重复登记为自己的新错误；子运行可重试时父运行也保留可重试状态。

### D-07 正常缺项形成可继续等待

复用 LangGraph 和现有 `waiting`，在 `WaitingRefV1` 增加 `business-preparation` 分支，字段为 `stage`、准备引用及闭合 `missingKinds`（资料、知识、评分配置、处置配置、预测配置、校准配置或人工审核）。`ResumeCauseV1` 增加 `business-preparation-ready`，只接收当前等待所绑定的准备引用；服务端重查实际就绪情况，不接收客户端自述已就绪。

未开始阶段缺项可补齐后继续；需要改变已冻结输入时创建关联的新准备/后续尝试，不覆盖原已完成事实。输入矛盾、单位错误和业务冲突使用明确结果；模型预算耗尽的旧终态不复活，沿用可复用的已完成上游，通过新的关联任务处理剩余工作。UI 在启动前展示缺项，后台仍保存等待，避免旧页面误把未齐备工作启动成终态失败。

未冻结的评分依据按本次准备时刻查询已登记发布，业务有效时点仍取原运行的validAt；A1成功后将精确assessmentBasisReleaseSetRef保存到原run-state，后续阶段和恢复读取该引用，不重新选版。运行详情通过既有resume-run命令提交当前等待的preparationRef与状态版本，服务端复查准备结果。

### D-08 单份运行清单

复用 deployment 的 `projects[].policyRefs` 为单向配置成员清单，按阶段列成员并解析一次；catalog 负责各成员真实正文。新配置去掉子策略 `policySetRef` 的反向父绑定、`budgetPolicyRef` 与内联预算同时维护等重复事实，预算正文从唯一 catalog 引用解析。既有配置的解码器将重复字段归一为相同运行对象，仅保留历史读取，不运行第二套权限/配置机制。

新检索审阅策略使用V2：预算目录中的 `AgentTaskBudgetPolicyV1` 为模型、提示、工具引用及数值预算的唯一来源，审阅策略只引用该预算及候选/补搜业务参数。解析时构造供原任务接口使用的完整对象，持久策略不重复抄字段；旧V1策略只在加载时归一。

同一目录归一方式用于清洗V3、知识编制V2、处置Agent V2和校准V2；清洗V2已用于documentRules，因此预算引用版用V3。它们保留原业务参数，只在catalog按budgetPolicyRef补出原运行对象。候选策略成员的policySetRef作为旧数据可选读取字段，成员归属由运行清单单向指定，实际运行和结果仍记录清单版本。

候选生成使用其既有RiskCandidateGenerationBudgetV1预算形状，在同一budgetPolicies目录以risk-candidate-budget登记；生成策略V2只保留budgetPolicyRef，加载时归一为原V1运行对象，保持原token、候选、纠错与墙钟限制。

批准元数据保留 `approvedBy/approvedAt` 和规则版本，移除 `approval.releaseId === software.releaseId` 的要求；软件清单记录所用配置。能力就绪按阶段判断，缺少校准配置可显示校准待准备，不把已经具备评分条件的模块置为全局不可用。保持硬预算，预算变化仅用于新任务；本 change 不自动提高现场数值预算。

### D-09 评分输入与下游策略分离

保留旧 `AssessmentInputSnapshotV1` 的历史解析，新增 `AssessmentInputSnapshotV2`（`schemaVersion: "2"`）：保留准备、创建者、时间、授权和审计字段；业务引用仅为 indicatorSystem、indicatorFieldMapping、applicableRuleSet、weightSet、scoringStrategy、riskMatrix、riskAcceptanceThreshold、monitoringWarningThreshold、jointTriggerPolicy 九项。公开加载结果为显式 V1/V2 联合，新写入只写 V2；纯计算从两者提取相同评分输入。删除另一份手工22字段列表，字段清单由 Schema 和实际消费推导。

C18 原 resolver 增加 `purpose=full|assessment|response|forecast|deviation`：full 保留11类；assessment 要求八类评分触发配置，response 在评分基准上加措施库，forecast/deviation 分别解析对应策略及其实际声明依赖。C19 适用规则集只绑定 assessment 集合。新调用显式传 purpose，旧持久集合不重写。

预警 open 只接收评估记录，服务端在本阶段从选定运行清单取得归集与通知策略，保存到原预警上下文。处置、预测、偏差、校准分别在原候选/输入/事实记录中保存自身策略及所追溯评估引用。策略缺失按 D-07 等待。首次阶段准备后不因软件或无关策略变更而重新选版；重放用原冻结策略。C25 精确结果 reader 不再承诺尚未发生的偏差/校准策略。

处置查询的措施库引用可省略，由服务端通过C18的response集合解析；显式引用仍须匹配本阶段选择。C27读取端注入C18配置解析与运行清单策略，已有候选查询直接按原收据重放。C28按阶段已冻结的策略引用读取C18正式成员，评分矩阵和指标仍取原评估依据；反馈记录保存首次确定的偏差及校准引用，历史记录允许缺席这些字段。预测输入保存到原运行状态，A2及恢复复用A0的输入。

C27的create-candidate和validate-and-record允许省略策略引用，分别读取原候选/候选查询冻结的generationPolicyRef与validationPolicyRef；显式提供时仍须匹配。A7的任务宿主复用现有readMeasureCandidateSet取得冻结Agent策略并从catalog精确读取，A8复用候选查询冻结策略，两阶段不再读取评估时的十项运行策略。

C18精确已发布成员读取从C16发布与原配置修订登记定位正文，不以该成员曾被某个配置集合物化为前提；预测和偏差策略可以在各自阶段第一次读取。C19委托同一读取接口，移除扫描历史评分集合的重复实现。工程、精确发布、原配置Schema及当前正文权限继续检查。

校准入口首次解析的target与Agent策略、A3已准备的精确输入引用保存在原run-state；A4及等待续办直接复用。校准任务宿主接收该冻结Agent策略，历史run-state缺少字段时按原准备路径读取，不增加策略影子表或新迁移。

### D-10 输出纠错使用既有 Agent 循环

复用网关现有错误码、`rawResponseRef` 与 token counts，JSON/Schema输出错误由 C08/C22 既有分类映射为 `repairable`。保持网关的传输 `retryable` 与候选可修正性分开；adapter 不重发，运行时在原模型/提示及剩余修正、token、时间预算内生成下一候选。每次实际响应和用量先保存结算，再决定下一步；不因解析错误漏记已发生用量。

`cleaningActionSchemaFor` 为每个任务按冻结资料顺序生成 `sourceOption` 短序号；宿主映射实际引用，内部工具仍使用原精确版本。页码、offset 和已读进度由宿主更新，模型不能指定任意工件路径。未登记工具、真实撤权和来源资格失效仍拒绝；普通选择序号或字段错误可反馈修正。保持同一运行时，不另建解析修补/无限重试循环。

### D-11 资料策略只表达业务质量

转换保留完整结构、坐标及失败资料段，C15 清洗决定使用范围。新清洗策略按转换输入类型选择规则：CSV/XLSX要求表格，不要求章节；PDF/DOCX/图片使用实际存在的正文/表格结构，已识别空白页不作为正文缺失。关键字段、保护段和原数值保持，普通段排除可得到 partial；新策略不使用全段100%留存作为通用可用前提，全部正文排空仍不可用。

用 `documentRules` 的 inputKind 判别配置取代三份逐个版本允许清单，输入引用与解析器真实版本照常记录，兼容性在导入/转换登记处处理一次。旧策略只解码为对应规则，不改历史结果。置信度沿已实施 D-92 的参与依据规则：单候选无合并时不要求多来源合并依据；不改既有数值权重、检索阈值或强制人工复核。

新 `DataCleaningPolicyV2` 使用原策略身份、保护段规则及关键字段覆盖要求，`documentRules` 每项固定一个真实转换inputKind与 `requiredSegmentKinds`；inputKind在一套策略中唯一。移除三份精确版本允许清单及普通段保留率门槛，全部正文为空仍由业务可用性判为不可用；旧V1只按其原含义解码供历史重放。新策略样例将CSV/XLSX绑定table，其余类型要求至少一种实际正文/表格种类，空白页无独立正文义务。

### D-12 编号、分页和错误

已有对象 ID 不迁移。新 C21 工件集/模型上下文在业务结果登记时使用短 UUID，父工作项、任务与检索集通过已有显式引用关联；任务冻结先于启动的 C08 身份继续复用 `agentTaskRefFor`，不破坏冻结引用。去掉从 ID 前缀或层层拼接反推关系的逻辑，历史 loader 按原完整引用读取。

分页沿现有 createdAt/taskId 等排序键，游标只承载页类型、工程/筛选及必要排序键；移除完整权限摘要绑定。每页重新执行查询入口可见性筛选。共享 decoder 验证组成字段及当前工程/筛选，不另加小于合法编码的512字符门槛；整体请求大小沿已有 HTTP 资源限制。新旧游标在切换时由页面清空重新从首屏读取，不迁移数据库游标。

详情直接调用精确 detail，不从 list.items 第一页寻找。未知技术异常映射既有 transient/terminal 技术错误和诊断引用，不折叠成 AUTHORIZATION_DENIED；无工程权限保持拒绝，工程内可按业务需要区分缺失和失败。七态视图复用，单在途刷新、焦点和键盘可访问性保持。

detail 的目标允许使用 URL 已有的 `{kind: "agent-task", reference: {entityId, versionId}}`，服务端按这两个字段读取登记的完整任务引用；其它行动、候选及启动接口继续使用完整引用。Provider 统一持有该选择并在 detail 返回后取得完整引用，不增加页面轮询。

### D-13 确定性组合复用原治理事实

新增 `KnowledgeReleaseV2` 的 `publicationOrigin` 联合：`human-reviewed` 携带原复核任务/决定；`derived-approved` 携带 `parentReleaseRefs`、`derivationPolicyRef` 和精确 `contextRef`。旧人工发布由行读取映射为 human-reviewed，不改写原发布。

仅 C17 检索证据组合和 C19 适用规则组装可在内部事务调用 `publishDerivedRelease`。该方法不是 HTTP/Agent 工具，不提供跳过审核开关；先使用原确定性算法取得批准成员和完整筛选结论，再将原修订、发布、成员绑定、命令回执、审计和原知识发布事件一同提交。内容、适用条件或冲突决定需要变化时先走原人工内容审核。C19 原 assemble HTTP 分支成功返回正式派生 release 和 basis 引用，客户端不再发 request-review/publish 的机械组合命令。

C19解析评分依据时，当前准备尚无派生规则集但配置和批准规则齐备，则复用同一组装方法形成该准备的派生发布，再解析正式依据；缺少业务配置或存在规则冲突时保持正常等待或原业务阻断。新准备不依赖另一准备的派生引用，也无需用户重复执行机械组装。

检索组合按批准成员及组装条件去重；适用规则集按准备上下文分组，不覆盖另一地层/工序准备。复用原 `KnowledgeReleaseRefV1` 作为引用形状，升级发布正文而非引入第二套发布引用。旧人工发布、独立内容审核、停用决定和回滚事实继续有效。一般语义定义的时间线规则保持，派生适用规则集按 contextRef 选择和约束。

### D-14 唯一迁移及历史读取

计划新增 `knowledge-modeling/reduce-defensive-design-overhead/000059_derived_knowledge_release_origin.ts`，实施前重核全局序号。迁移承担发布来源及D-05批准条目登记：`business.knowledge_releases`新增可空 `publication_origin jsonb`、`derivation_scope_key text`，允许原 review 两列为空；更新原 JSON/check 约束，合法行恰为“origin为空且两项人工引用存在”或“origin为derived-approved、定义类型仅限两类、两项人工引用为空”。来源 JSON 不复制人工引用，V2 reader 从旧两列构造 human-reviewed，从新 origin 构造派生分支。`business.identification_knowledge_entries`按工程、精确发布及条目编号保存原批准正文与来源；发布事务同时登记，旧发布由受权的原包读取补登记。该表只提供原事实的条目读面，不改变原包和向量编号。

`derivation_scope_key` 只用于派生 applicable-rule-set，由正式 contextRef、批准父发布集合、评分配置集合及组装策略的规范引用元组产生，不接受客户端指定；相同准备使用新批准规则时可以生成新的派生版本。原 `knowledge_releases_effective_uidx` 改为 scope为空时的原唯一约束和 scope非空时 `(definition_id, derivation_scope_key, effective_from)` 唯一索引。现有 FK、只追加及审核链接触发器保留；派生分支不插入虚假 `knowledge_review_links`。组合幂等先按正式输入和 context 查已有发布，避免并发重复。

V1历史集合和评分快照不迁移正文；现有访问记录和 causal授权历史不删除。测试覆盖迁移前人工发布、迁移后两类发布、异适用性并存和外键读取。已有派生记录后禁止直接回退到只能解析人工发布的软件；回退通过既有独立运维流程选择兼容版本或隔离恢复点。迁移仅在隔离测试数据库验证，现场迁移与备份留到部署阶段。

### D-15 在途 change 的责任转移

### D-16 验证与工程说明

复用既有测试，按业务结果更新断言。删除只证明已取消的身份配对、重复哈希或完整授权摘要相等的用例；保留账号可见性、事务、重复写入、取消、评分和人工决定测试。性能只比较相同输入的原件首字节/完成时间、检索延迟及阶段续办，不为每个检查建立新监控系统。

## Risks / Trade-offs

代际与权限解耦必须在两路召回前使用相同成员集合，否则会改变可见成员的排序质量；用既有检索质量集验证。移除文件验真后不再检测系统外替换文件，符合本次场景，独立备份恢复仍可显式核验。旧终态失败不能直接恢复，需要关联新尝试；这保护历史与预算事实。

减少职责的收益按实际链路测量，不预填工期或性能比例。现有 dirty 不是角色交接检查点，实施前需核对后续实际基线；本轮不自行提交 Git。

## Migration Plan

实施顺序为 IP-01 → IP-02 → IP-03/IP-04/IP-05 → IP-06/IP-07 → IP-08；共享 contracts、start.mjs 和迁移测试由同一实施轮次串行整合。新旧客户端与 API 同次发布，不维护两套公开写接口；旧持久数据仅保留必要 reader。
