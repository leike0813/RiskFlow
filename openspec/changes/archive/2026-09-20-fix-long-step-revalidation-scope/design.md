# Design

## Context

- `controlledMutation` 把 `revision`（起始事实集哈希）交给 perform；集成的主线复验步骤在 `lock.withoutLock(...)` 后调用事后校验。
- `collectStatus` 的事实集包含工作树脏状态与脏路径，因此长步骤自身的构建/测试产物（未跟踪文件、临时目录）会短暂改变事实集。
- 实测：C17 的主线复验通过后仍被判 `stale_revision`；事后 main 与两个 worktree 均干净。

## Goals / Non-Goals

**Goals:**

- 事后校验只覆盖该步骤依赖的不变量，避免自伤。
- 保留对真正并发的拒绝能力。

**Non-Goals:**

- 不取消事后校验，也不改为"永不校验"。
- 不改变锁让出/重新获取的语义与重试预算。
- 不试图清理长步骤产生的临时文件（那是各工具自身的职责）。

## Decisions

**D1：按不变量校验，而不是按全量哈希。**
`expectedRevision` 对"读—决策"阶段是合适的乐观并发标记，但对"锁外执行长步骤"不合适：它把与决策无关、且可能由步骤自身造成的差异也算作并发冲突。改为比对四类不变量：工作项状态、`checkpoints.taskId`、`main.head`、违规集合。

**D2：拒绝语义与错误码不变。**
仍抛 `stale_revision`，仍指引重新读取状态；调用方与既有回执/幂等语义无需改变。

## Risks / Trade-offs

- 收窄后，纯工作树脏状态变化（例如他人手工改动某个 worktree 的未跟踪文件）不再阻止写入；但这类变化不影响集成步骤的正确性（它只关心主线 HEAD 与工作项阶段），且会被后续状态的 violations 判定捕获。
- 若未来某个长步骤依赖其它事实（例如需要比对某个具体 schema 版本），应把该事实加入校验清单，而不是退回全量哈希。
