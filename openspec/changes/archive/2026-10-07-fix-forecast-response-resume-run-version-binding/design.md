## Context

C30 的恢复入口以「预期状态版本」作为并发与陈旧断言：`resume` 先读运行游标，再要求 `cursor.runVersionId === command.expectedRunVersionId`，阶段提交时又以游标版本复验最新已登记的 `run_version_id`（design D-08）。该断言本身正确，必须保留。

问题出在「调用方拿得到什么」。`startRun` 进入等待态时，公共等待结果只交出 `workflowRunRef`（其 `versionId` 是运行登记摘要），没有交出运行停在等待点时的**运行状态版本**。C41 于是把 `forecastRunRef.reference.versionId` 当成 `expectedStateVersion` 提交，两者语义不同，等待点之后运行还会推进到 assessment 阶段，于是恢复必然版本冲突。C41 的绑定与终局决定记录里也没有这个值，恢复路径之间无法互相核对。

已确认的现状事实：`resume` 读取游标失败报 `RUN_NOT_FOUND`（游标身份/授权不符时同形）；版本不符报 `STALE_VERSION` 并由调用层映射为稳定并发失败；`business.workflow_graph_results.run_version_id` 与运行状态正文的 `runVersionId` 已承载该版本，不需要新增表或迁移。

## Goals / Non-Goals

**Goals:**

- 让 C30 在等待结果里交出等待点状态版本，使 C41 能按契约取得恢复所需的值。
- 让 C41 的采纳绑定与终局决定冻结同一份等待点状态版本，并在恢复时使用它。
- 保持「预期状态版本陈旧即拒绝」「同键异载荷即拒绝」「恢复沿用原线程与冻结身份」全部不变。

**Non-Goals:**

- 不放宽任何版本或幂等断言，不把「陈旧」降级为警告。
- 不新增表、索引、迁移或依赖。
- 不改动 C25/C26/C27/C28 的领域事实语义与写入协议；本 change 只补公共端口上缺失的一个值。
- 不处理 C41 其它接缝缺陷（授权签发身份、回执身份），那些已在 C34 交付内修复。

## Decisions

### D-01：等待结果新增 `waitStateVersion`，与等待引用同源交出

`startRun` 的等待分支在返回 `waiting` + `workflowRunRef` 的同时交出 `waitStateVersion`，取值就是本次调用结束时运行游标的 `runVersionId`。

- 理由：等待点版本是运行时自己算出的事实，让它自报可避免调用方二次读取状态（多一次受控读、一次授权、一次身份绑定），也避免调用方猜「最新」。
- 考虑过的替代方案：(a) 调用方在恢复前另发一次 `readLatestRunState`——多一次读与授权，且把「恢复前状态」与「决定冻结时的状态」分成两个口径，绑定与恢复之间仍可能出现无法解释的差异；(b) 把 `workflowRunRef.versionId` 改成状态版本——运行登记身份本身也是要保留的事实，改语义会让已归档引用不可比；(c) 允许 `expectedStateVersion` 为空表示「不校验」——违反 D-08 的既有断言，拒绝。
- 代价：公共等待结果联合多一个可选字段；模块化结果 Schema 的等待变体需要一个更明确的伴随事实注释。

### D-02：等待点版本为可选，缺失时恢复按既有陈旧规则失败

`waitStateVersion` 在等待结果里是可选的：无法给出等待点版本时不编造值，调用方也不得以运行登记摘要代替。

- 理由：可选 + 失败闭合保证旧调用方与无法给出状态的运行都走既有拒绝路径，而不是被静默放行或降级校验。
- 代价：缺该值的运行无法完成 C41 采纳恢复；这比让恢复误判为成功更安全。

### D-03：绑定与终局决定各冻结一份同值字段，恢复只读绑定

`VerifiedResponseWorkflowBindingV1` 与 `HumanResponseDecisionV1` 各增一个可选的等待点状态版本字段。采纳路径把 `startRun` 交出的值同时写入两份记录；`#resumeForecastRun` 只从绑定读取该值。

- 理由：两份记录都可能被单独回读（绑定证明按绑定回读，恢复按决定回读），只改一处会让两条恢复路径出现两个口径。把值放进两份记录后，任一路径都能独立校验，且「绑定里的版本」与「决定里的版本」不一致时可在恢复前失败闭合。
- 考虑过的替代方案：只在决定里保存，恢复时用 `decision.forecastRunStateVersionId`——绑定证明仍无法核对，会退回「不校验」。拒绝。
- 代价：C41 记录 Schema 变宽；历史记录缺该值时按 D-02 失败闭合，不回填。

### D-04：绑定证明核对版本归属，拒绝跨运行取值

C30 精确绑定证明在回读绑定时，核对冻结的等待点状态版本属于该绑定的 `forecastRunRef` 指向的同一运行；错配或缺失即失败闭合。

- 理由：绑定是跨模块传递的事实，核对归属是防止「拿 A 运行的版本恢复 B 运行」的最低成本断言。
- 代价：绑定证明端口的返回联合需要能表达「版本不可用」，按既有失败形态返回即可，不新增错误码。

### D-05：恢复断言一字不改

`expectedRunVersionId` 的比对位置、运行级版本断言、阶段提交时的游标复验全部保持现状；本 change 只改变 C41 传入的值。

- 理由：这是本次问题的根因边界；改断言等于用放宽门禁掩盖接线错误。

## Risks / Trade-offs

- **等待点版本与恢复之间运行被推进**：此时恢复按既有规则版本冲突拒绝，是期望行为（不能越过等待门），但会让 C41 在极端并发下需要同命令身份重试。重试沿用原命令与同一等待点版本，不会改按最新版本继续。
- **公共等待结果变宽**：模块化结果 Schema 的等待变体新增可选字段会影响所有使用 `moduleResultSchema(..., true)` 的模块的解析面；均为可选字段，既有序列化不受影响，需回归 runtime 与 adapter 测试。
- **两份记录可能分叉**：由 D-03 的恢复前核对收口，任何分叉都表现为失败闭合而不是错误恢复。

## Migration Plan

不涉及表结构、迁移与数据回填。历史绑定与决定记录缺等待点状态版本，恢复按 D-02 失败闭合；如需为在途运行恢复，只能由人工以同命令身份重试并重新取得等待结果，不得回填历史版本。

## Open Questions

无。等待点版本的取值口径、字段归属与失败形态均已在上文定死。
