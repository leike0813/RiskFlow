# RiskFlow Agent-native 横切运行与治理契约

> 状态：Wayfinder 已确认的规划基线；本文不替代后续 OpenSpec 正式规格。
>
> 适用范围：资料接入、知识建模、风险识别、风险评估与预警、处置反馈、版本治理和智能 Agent 用户交互。

## 1. 契约目标

RiskFlow 只在需要语义判断、证据取舍或受限工具行动的环节设置必经 Agent 任务。P/C 计算、风险矩阵映射、阈值判断、Schema 校验、业务入库、版本发布和回滚等确定性阶段不以 Agent 可用性为前置，也不得由 Agent 改写结果。

Agent-native 的通用形态是：

```text
冻结的确定性基线
  → Agent 审阅或候选生成
  → 任务类型化 Agent 增量
  → 独立确定性校验与选择
  → 候选工件或正式业务产物
```

这条形态不表示每个阶段都要调用模型。只有本契约列出的任务类型进入统一 Agent 任务模块；其它 LLM 节点、确定性模块和人工复核保持各自边界。

## 2. 三类智能行为必须分开

### 2.1 Agent 任务

Agent 任务是一次有界的智能执行过程，可以读取冻结基线、调用任务允许的领域工具并输出 Agent 增量。它按触发方式分为：

- **内嵌任务**：由已经确认的业务运行自动触发，在预授权的任务策略内执行，不逐次要求用户确认；
- **交互任务**：由停靠栏或全屏工作台触发，继承当前用户和页面上下文，提交写命令前要求用户确认。

两者共用任务身份、状态、工具、预算、审计、失败和持久化契约，不建设两套 Agent 运行模型。

### 2.2 专用 LLM 节点

专用 LLM 节点只执行一次结构化模型调用，不拥有工具循环或业务命令能力。风险识别中的 RI-S57 风险候选生成继续采用专用 LLM 节点；其输出直接进入独立确定性校验，不再交给同一 Agent 作形式上的第二次审阅。

### 2.3 人工复核

人工复核由复核人对确定对象版本作出类型化决定。Agent 任务不能冒充复核人，不能发布、批准、采纳、作废或回滚业务对象，也不能用同模型自审自批代替独立制衡。

## 3. 必经 Agent 覆盖矩阵

| 业务环节 | 冻结基线 | Agent 是否必经 | Agent 产物 | 确定性收口与正式性 |
|---|---|---:|---|---|
| 数据清洗与部分可用判断 | 原始工程资料版本或监测批次、解析结果、可用清洗工具 | 是 | 清洗增量、质量判断、排除范围和覆盖依据 | 校验结构、权限、字段类型、资料段标识和审计完整性；通过后形成版本化清洗结果 |
| 非结构化知识编制 | 工程资料、规范、案例、既有知识修订及证据 | 是 | 工序模型、机理、评分规则或措施项候选增量 | 校验 Schema、引用、关系、一致性和完整性；正式发布必须人工确认 |
| 甲方已审核配置包原样导入 | 已审核版本化配置包 | 否 | 无需 Agent 重新解释 | 只执行确定性 Schema、引用、版本、权限和完整性校验；正式发布必须人工确认 |
| 识别检索审阅 | 确定性 BM25/向量融合基线、关系上下文和检索策略 | 是 | 补充检索、候选处置和覆盖判断增量 | 确定性校验工具行动、融合、去重和上下文预算，形成最终推理上下文 |
| RI-S57 风险候选生成 | RI-S56 五项上下文 | 否，使用专用 LLM 节点 | 模型输出候选 | Schema、证据、规则、合并和综合置信度校验；失败转人工复核 |
| 风险评估与预警 | 冻结评估输入、已发布规则和监测快照 | 否 | Agent 只可交互解释 | 指标映射、P/C、矩阵、四类触发和入库全部确定性完成 |
| 处置建议生成 | 已发布措施候选集、风险事件、适用性元数据和触发指标 | 是 | 措施选择、组合、顺序、资源和目标指标增量 | 三项约束全部通过后形成正式处置建议；采纳和执行由人决定 |
| 偏差超限后的校准建议 | 已入库偏差记录、预测与反馈、规则/权重/阈值版本和证据 | 是 | 偏差原因和建议调整对象增量 | 结构与引用校验后形成校准建议候选并进入人工复核；不得直接改变生效版本 |
| 版本发布、停用与回滚 | 待发布定义与审核决定 | 否 | Agent 可解释差异或准备命令 | 授权用户通过正式领域命令决定，Agent 无权自动执行 |
| 用户查询、解释与命令准备 | 当前页面对象和授权查询投影 | 按用户发起 | 回答、深链或命令提案 | 回答引用正式对象；写命令经用户确认后调用原领域接口 |

MVP 必须真实跑通表中的五类必经内嵌任务：数据清洗、非结构化知识编制、检索审阅、处置建议和校准建议。

## 4. 统一 Agent 任务模块

Agent 任务模块是一个深模块。调用方只提交任务信封并获得任务结果引用，不接触模型消息格式、工具循环、上下文裁剪、重试或持久化实现。

建议的外部接口形态：

```text
startAgentTask(taskEnvelope) -> agentTaskRef
getAgentTask(agentTaskRef) -> agentTaskView
resumeAgentTask(agentTaskRef) -> agentTaskRef
cancelAgentTask(agentTaskRef) -> agentTaskRef
confirmAgentCommand(agentTaskRef, commandProposalRef) -> domainCommandResultRef
```

任务信封至少固定：

- 任务类型与触发方式；
- 发起者、工程和父业务运行；
- 冻结基线、输入对象和精确版本引用；
- 模型部署与提示模板版本；
- Agent 工具策略和资源预算版本；
- 领域增量 Schema 与确定性校验策略版本；
- 业务幂等键和因果运行引用。

任务结果只返回状态、阶段、增量、候选、校验、错误、正式结果和审计工件引用，不复制完整业务实体或原始资料。

各业务模块负责定义自己的任务策略、工具、增量和校验接口；Agent 任务模块负责统一运行。不得为五类必经任务各建一套工具循环、状态机或审计模型。

## 5. 状态与有限运行

Agent 会话可以持续存在，但每个 Agent 任务必须有界并进入终态。状态统一为：

```text
待运行 → 运行中 → 已完成
              ↘ 等待用户确认 → 运行中 / 已取消
              ↘ 可重试失败 → 运行中
              ↘ 终止失败 / 已取消
```

- “等待用户确认”只用于交互任务准备的正式写命令；
- 阶段、失败原因、已用/剩余预算和恢复条件使用结构化字段表达，不扩张状态枚举；
- Agent 生成需要人工复核的候选后，Agent 任务本身结束，由独立复核任务承接人的决定；
- 父 LangGraph 运行可以等待复核，但不能让 Agent 任务长期占用模型或 Worker；
- 取消不回滚已经可靠形成的业务事实、候选工件或审计事件。

## 6. 工具与权限

每个任务类型绑定版本化 Agent 工具策略。策略只暴露完成任务所需的少量领域能力，不暴露通用数据库、文件系统、Shell、任意网络请求或外部系统接口。

权限规则保持简单：

1. 创建任务时按当前用户、工程和资料权限校验一次；
2. 本次输入限定为通过校验的任务上下文，工具限定为任务白名单；
3. 任务启动后按既定上下文运行到终态，不建设动态撤权或逐工具调用复验；
4. 交互 Agent 提交正式领域命令时，沿用该命令已有的普通权限校验；
5. Agent 不能通过工具策略获得超出发起者的业务权限。

工具必须以领域目的命名并返回版本化结构结果，例如“读取资料段”“补充检索证据”“读取已发布措施候选”，不得暴露“执行 SQL”“读取任意文件”“调用任意 URL”等浅接口。

## 7. 版本化资源预算

每类 Agent 任务冻结由系统强制执行的硬预算，至少包括：

- 最大模型调用次数；
- 最大工具调用次数及每种工具的单独上限；
- 最大输入上下文和输出规模；
- 最大候选数、处理对象数和补充检索轮次；
- 最大墙钟时间；
- 允许使用的模型和并发数。

Agent 可以提前结束，但不能自行扩容、切换模型或改变预算。后续调参只能发布新预算策略；运行中和历史任务继续引用原版本。

## 8. Agent 增量

Agent 相对冻结基线的影响必须表达为任务类型化领域操作，不使用通用 JSON Patch、整对象覆盖或仅有自然语言的修改说明。

| 任务类型 | 允许的领域操作示例 | 明确禁止 |
|---|---|---|
| 数据清洗 | 修正字段、单位换算、标记异常、处理缺失、生成摘要、排除资料段、判断部分可用 | 改写 raw、删除原批次、越过结构硬约束 |
| 知识编制 | 新增候选条目、修订候选字段、补充证据、建立候选关系、标记不确定项 | 修改已发布版本、发布或回滚、伪造证据 |
| 检索审阅 | 补充候选、保留、提升、降级、标记重复、疑似无关、适用性不确定或冲突 | 改写基线分数、删除硬性冲突证据、改变权限或发布状态 |
| 处置建议 | 选择候选措施、组合、排序、填写资源需求和目标指标 | 生成候选集外措施、覆盖三项校验、批准执行 |
| 校准建议 | 指出偏差原因、建议调整对象、说明预期影响和证据 | 直接修改权重/阈值/区间、创建生效版本 |

确定性模块逐项记录接受、拒绝及原因，并引用最后形成的候选或正式产物。Agent 声称的影响与系统实际接受的影响必须可以分别查询。

## 9. 确定性校验与有限修正

Agent 输出先形成不可变候选版本，再由业务模块的独立确定性校验器处理。校验器可以把以下结构化问题返回同一 Agent，在原预算内生成新候选版本：

- 字段缺失或格式错误；
- 引用失效；
- 候选越过冻结集合；
- 任务类型化增量不完整。

以下阻断不得通过 Agent 循环尝试绕过：

- 权限不足或来源无资格；
- 输入或发布版本不兼容；
- 规则冲突；
- 处置建议的触发指标一致性、规范合规性或现场可执行性校验失败；
- 任何要求人工发布、批准或复核的条件。

每轮候选和增量差异均保留。修正次数达到预算上限后，按业务阶段进入人工复核、暂停或终止失败。该机制是外部确定性校验后的受限修正，不是同模型自审自批。

## 10. 失败、重试与恢复

必经 Agent 任务失败时不能跳过 Agent 使用确定性基线继续，也不能静默切换模型、提示模板、工具、预算或输入版本。

- 瞬时模型或工具错误只在冻结策略和剩余预算内重试；
- 模型不可用、预算耗尽或重试耗尽时，保存基线、Agent 增量、候选、工具结果和结构化失败原因；
- 可恢复情况进入可重试失败，原任务恢复时继续使用原输入和策略；
- 需要新模型、新预算、新输入或新工具策略时创建新任务，并引用原任务作为原因；
- 交互 Agent 不可用时显示技术阻断，不生成降级回答冒充结果；
- 已可靠入库的预警信息、偏差记录及其它上游事实不因下游 Agent 失败而回滚。

## 11. 人工生效边界

不为所有 Agent 任务增加统一人工批准门槛。生效规则按产物类型确定：

- 数据清洗结果通过硬约束后自动成为业务可用输入；
- 检索增量通过确定性选择器后自动影响本次推理上下文；
- 处置建议候选通过三项约束后自动形成正式“建议”，但采纳和现场执行由人决定；
- 知识候选必须人工审核发布；
- 校准建议必须人工复核，且只能据此创建受治理定义的新草稿；
- 交互 Agent 的写命令必须先显示工程、对象、精确版本、预计结果和外部副作用，再由用户确认。

同一账号可以兼任提交与审核职责，但每次正式发布、采纳、执行和复核决定都要形成独立审计事实。

## 12. 审计与持久化

每次 Agent 任务至少记录：

- 任务身份、类型、触发方式、发起者、工程、父运行和业务幂等键；
- 冻结基线、输入对象与精确版本；
- 模型部署、参数、提示模板、工具策略、预算和增量 Schema 版本；
- 每一步结构化行动、工具名称与版本、调用参数、结果引用、耗时和资源消耗；
- 每个候选版本、Agent 增量、确定性校验、接受/拒绝结果与原因；
- 命令提案、用户确认或拒绝、正式命令结果与业务对象引用；
- 错误、重试、恢复、取消和终态。

实际渲染给模型的输入、原始模型响应及必要的工具观察快照作为受权限保护的不可变内容工件保存。PostgreSQL 保存工件哈希、权限、来源和精确引用；能够引用既有资料段或业务事实的证据正文不重复复制。

不保存模型内部思维链。界面只展示系统实际观察到的任务步骤、工具行动、增量、校验和结果。

Agent 运行工件和 Agent 增量不是风险、评估、预警、处置或复核事实。清理检查点或会话缓存不得删除 Agent 审计工件及其业务结果引用。

## 13. LangGraph 与领域模块边界

LangGraph 负责任务编排、状态转换、检查点、重试和暂停恢复；Agent 任务模块负责有界模型与工具运行；领域模块负责基线、工具接口、确定性校验和正式业务写入。

图状态只保存 `agentTaskRef`、候选引用、校验引用、状态、阶段和错误，不保存原始提示、响应、完整工具结果或大体积增量。检查点恢复先查询既有 Agent 任务和候选，避免重复模型调用或工具副作用。

Agent 任务模块不成为跨层后门：

- 数据清洗工具只调用工程数据模块公开接口；
- 知识编制工具只调用知识建模模块公开接口；
- 检索工具只调用混合检索和关系上下文接口；
- 处置与校准工具只调用预警处置模块公开接口；
- 交互 Agent 只查询公开投影并准备正式领域命令。

常规 `assessmentGraph` 的指标取值、P/C、矩阵和预警阶段不创建 Agent 任务。Agent 可以解释其已入库结果，但不能插入计算链或成为评估可用性依赖。

## 14. 界面契约

停靠栏和全屏工作台共享同一会话与 Agent 任务状态。Agent 任务详情至少展示：

- 任务类型、触发方式、发起者、工程、父业务运行和状态；
- 冻结基线、模型、提示模板、工具策略和预算版本；
- 已用/剩余模型、工具、上下文和时间预算；
- 可审计步骤与工具调用，不展示模型内部思维链；
- Agent 增量及每项接受、拒绝和原因；
- 候选、确定性校验、失败与恢复入口；
- 正式业务对象、复核任务或命令确认卡片的深链。

模型服务不可用、必经 Agent 失败或预算耗尽时显示明确阻断；不得用普通聊天回答、旧任务结果或确定性基线冒充本次正式结果。

内嵌 Agent 任务同样出现在对应接入、知识、识别、处置和校准运行详情中。用户无需打开工作台才能知道 Agent 是否运行、使用了什么策略以及对结果产生了什么影响。

## 15. MVP 落地与验收

MVP 共用一个 Agent 任务运行模块，提供五个内嵌任务策略和一个交互入口。每种内嵌任务至少使用固定验收样例真实运行一次：

1. 清洗一批地表沉降监测数据并形成可追溯清洗增量；
2. 从至少一条真实或甲方认可的规范或工程资料编制知识候选；
3. 对一个工序工作项完成基线检索、Agent 审阅、有界补搜和确定性上下文选择；
4. 在小规模已发布措施候选集中形成处置建议并通过三项校验；
5. 对一条偏差超限记录形成校准建议候选并进入人工复核。

同时验证交互 Agent 能引用正式业务对象和证据、准备一个写命令、展示确认卡片，并在确认后调用原领域接口。

MVP 可以对每类任务只提供一套模型、工具策略和资源预算，不建设策略设计器、动态权限、自由联网、Shell、通用工具市场、多模型辩论、多角色自审或自动扩容。

稳定验收行为包括：

- 必经任务不可静默跳过；
- 预算由系统强制执行且历史任务固定引用原版本；
- 工具调用不越过任务白名单；
- 可修复错误只能在原预算内有限修正；
- 失败不回滚已入库上游事实；
- Agent 增量与系统接受结果可分别查询；
- 原始输入/输出可审计重建但不暴露思维链；
- Agent 不能改变 P/C、矩阵、阈值、发布和人工决定。

## 16. 对既有规划规格的修订

- 宏观架构：增加统一 Agent 任务模块，明确它与专用 LLM 节点、领域模块和 LangGraph 的缝隙。
- 领域模型：Agent 任务归入过程任务；Agent 增量和原始模型输入/输出属于运行审计工件，不是业务事实。
- MVP 定义：把五类必经内嵌任务与交互入口列入完成门槛。
- 功能规格：知识编制、检索审阅、处置建议和校准建议改为任务类型化 Agent 契约；评估预警明确无必经 Agent。
- 接入规格：数据清洗沿用 Agent 主导，但纳入统一工具、预算、增量、失败和审计契约。
- 识别工作流：I3 增加基线检索后的必经 Agent 审阅与有界补搜；RI-S57 后不新增第二次 Agent 审阅。
- 评估处置引擎：A0～A6 保持确定性；A7 使用处置建议 Agent；反馈偏差超限后使用校准建议 Agent。
- 界面规格：Agent 任务详情增加预算、增量、校验、失败和正式结果引用；各业务运行显示内嵌 Agent 子任务。

## 17. OpenSpec 交接要求

生产实现前，应以一个完整 OpenSpec change 先定义统一 Agent 任务能力及与现有图、领域模块的接口，再由后续实施 change 引用，避免各阶段重复搭建运行框架。正式规格至少覆盖：

- `AgentTaskEnvelope`、任务状态、结果与错误 Schema；
- 五类任务的策略、工具和 Agent 增量可辨识联合类型；
- 模型、提示模板、工具策略和预算不可变版本；
- 候选、确定性校验、有限修正和人工复核路由；
- PostgreSQL 任务/步骤/审计记录与不可变内容工件引用；
- LangGraph `agentTaskRef` 状态集成、幂等恢复和失败传播；
- 交互命令确认与原领域命令的复用；
- MVP 固定样例和稳定可观察验收行为。

该 change 不引入新的模型供应商、自由联网、Shell 或通用 Agent 平台依赖。具体包和版本必须在 OpenSpec 中另行评估并冻结。
