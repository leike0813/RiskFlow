# 业务对象 → 现有页面映射与新导航结构

Type: grilling
Status: resolved
Blocked by: 01

## Question

用户已指出重做最难的部分是「业务对象与现有页面的对应关系」。生产 `BUSINESS_ROUTE_SEEDS_V1` 有 49 条模板（含 2 条会话门禁），再加 base 的 `/knowledge` 与单独注入的 `/assessment/quality`，共 51 条现有模板；七项业务导航外还有 Agent 与系统管理入口。

**以业务对象为行、以现有路由为列，逐条判定新承载与精确 URL 的去向，并由此得出新的导航树** —— 页面合并不等于删除对象身份或历史地址。

具体要回答：

1. 以 `CONTEXT.md` 的风险闭环对象为准（标准化风险记录、风险评估记录、预警信息、预警处置任务、处置建议、处置反馈、偏差记录、校准建议、复核任务、审计事件、发布集合…），每个对象在界面上是**一个页面、几个页面、还是不需要独立页面**？判定依据是什么？
2. 现有 51 条模板逐条判定新承载与地址解析。特别处理这些高风险判定：
   - `/assessment/start` 这种纯表单页 —— 在新结构里是独立页面还是从上下文直接发起？
   - `/knowledge/*` 五个治理页 —— 治理职责该不该占主导航一级项？
   - `/ops/*` 五个系统管理页 —— 已定「系统管理不走业务导航」，那它们从哪进？
   - `/review-audit`、`/audit`、`/trace`、`/runs` 四个审计追溯页 —— 追溯是每个业务对象的详情内能力，还是仍要独立页？
   - `/reassessments`、`/matrix`、`/quality` 等二级入口 —— 合并还是保留？
3. 新导航树是什么？第一层是业务对象还是用户任务（"本工程今日风险""待我处置的预警""在跑的识别评估"）？Agent 停靠栏是否仍是导航项（已定：不是，是右侧停靠区 + 全屏工作台）？
4. 「工程风险管理员的日常主路径」在新导航下是哪条最短路径？从打开系统到处理完一条预警，点几下、经过几个页面？
5. 被判定删除的页面，其已有功能有没有落到新位置的缺口？

**不要**在这一票里定视觉令牌或组件细节。

## Answer

产出资产：[业务对象 → 页面映射与新导航结构](../../riskflow-master-plan/prototypes/business-object-page-mapping.md)。

**新导航树**：一级六项 —— 风险总览 / 工程 / 识别 / 评估 / 预警与处置 / 治理；辅助入口为全局搜索、右侧待办与智能助手、用户菜单中的系统管理。工程保留一级位，工程仍是权限与数据归属边界。日常主路径为风险总览 → 上传资料 → 启动识别 → 风险记录 → 评估 → 预警 → 处置任务。

**归位与身份契约**：

1. 纯表单在上下文中就地展开，原地址永久保留为解析入口，不保留第二套旧页面。`/assessment/start` 到待评估列表发起动作；执行登记进入处置任务的 `execution` 页签。
2. 处置闭环五条 `/response/*` 合并视觉承载，不删除所选子记录的身份。规范地址为 `/warnings/tasks/:taskId?version=:taskVersion&tab=:tab&recordKind=:kind&recordId=:id&recordVersion=:recordVersion`，另保留 `project/revision/assessmentSources`。任务引用与子记录引用分离；旧详情 `version` 是子记录版本，不能改名冒充任务版本。旧执行地址中的 `task/taskVersion` 与 `execution/version` 分别定位两种对象。页签直接精确读取所选记录，不在任务关系列表首页寻找它。
3. 评估记录与重评估列表合并，图谱去重复列表；矩阵落点进入评估详情。`/assessment/matrix` 仍是无导航的共享只读视图：有精确评估记录上下文时定位详情矩阵区，否则按所给冻结矩阵/输入引用读取，不跳任意当前记录，不造新的列表矩阵浏览器。
4. 复核队列进待办，但 `/review-audit/tasks/:taskId?version=:reviewTaskVersion` 精确 URL 永久保留。待办内打开为全屏覆盖层，直达/刷新为同视图全屏；返回/取消恢复合法短生命周期背景 URL，否则进入合法默认入口 `/overview`。历史已决定/已取代任务仍按精确引用窄读，不扫描 pending 队列。仅保留背景 URL，不缓存业务正文。识别复核旧地址解析至该视图，保全各类型的全部决定分支。
5. 审计和报告归治理但地址不改；追溯进入风险详情 `tab=trace`。旧 trace 的 `subject` 实际是风险记录 ID，不是通用类型判别联合。旧运行记录入口到 `/overview?tab=runs` 的有界运行摘要，旧复核根到 `/overview?tab=todo`；CH9 未就绪前保留原队列承载。
6. ui-spec 已规划未建的 8 页保留规划身份，不将其算成现有可解析路由或承诺已有实现。

**逐条清单与统计**：附件逐条列出 51 个现有模板的新落点：40 个规范承载（含 2 个会话门禁）+ 11 个永久旧解析入口，二者都仍可达；8 页规划另列。导航入口减少、旧页面实现移除与 URL 身份保留分别计数，撤销“约 24 条正式可达路由”的验收口径；约数只能用于工作量估计。

**分期与规格归属**：保留九个 CH 工作包，沿既有四个 web capability 与 `platform/web-shell-interaction-primitives` 写 delta；新增设计系统/总览/搜索与停靠区仅承载新行为，不按导航强行重划旧 capability。CH2 只准备公共路由/导航接缝及能力授权，不提前发布删旧入口的六导航或切断旧承载。CH3 接运行摘要；CH5 接风险追溯；CH6 接评估/重评估与矩阵；CH7 接处置子记录；CH9 接复核与待办。CH3–8 各自在新承载、权限和历史深链验收通过后，原子启用对应重定向并移除旧页面实现。CH9 可并行研究/开发，但最终六导航与停靠区的组合启用依赖 CH3–8 目标就绪；构建顺序不等于发布顺序。

**仍需施工闭合的风险**：

- 建议已有 `taskRef`，其它上游引用未必闭合任务关联；只有进入任务页签才要求该关联完整，缺失窄读由 CH7 所属域补齐。合法独立执行及后续反馈／校准保留原精确地址与共享独立视图，不能为了页面合并强制建任务。无权、关系不可证明或不存在同形拒绝，不泄露其它工程或解绑事实。
- 逐段精确匹配下，`/warnings/abc/actions` 不与 `/warnings/tasks/:taskId` 相交；真正交集 `/warnings/tasks/actions` 按首个不同段的静态优先规则归 tasks。禁止以参数数目/静态数目/字典序三键代替语义优先级，相同具体度的交集注册时拒绝。
- 总览聚合与列表必须同口径；复核合并不能压平六分支及其他类型决定；旧查询投影是否可下线须按真实调用者核对，不能由取消菜单入口推出。
